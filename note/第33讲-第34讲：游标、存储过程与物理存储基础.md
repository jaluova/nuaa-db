## 一、游标的完整操作流程

游标是处理多条记录的核心机制。当一个 `SELECT` 返回多行结果时，游标提供一个行指针，从第一行开始逐行读取。[00:00]

### 1.1 四步操作

游标的使用包含声明、打开、读取、关闭四个步骤：[00:29]

**（1）声明游标（DECLARE CURSOR）**

定义游标名称，绑定一条 `SELECT` 语句。游标可带参数（如课程号），结果集的结构（列数和类型）在声明时确定。[00:35]

```sql
DECLARE cursor_name CURSOR FOR
  SELECT sno, grade FROM sc WHERE cno = :course_no;
```

> [00:49] 实际上就是一条SQL语句产生一个结果集，然后用游标代替结果集的指针。

**（2）打开游标（OPEN）**

让 DBMS 根据游标定义执行 SQL，将结果集数据从服务器取回到内存缓存区。这一步才真正执行查询。[01:08]

> [01:06] 打开游标的概念才是把数据从服务器端取到你的前端。

**（3）逐行读取（FETCH ... INTO）**

每次读一行，将当前行的各列值赋给对应的主变量。通常配合循环，终止条件是遍历完所有行（指针到达结果集末尾）。[01:19]

```c
FETCH cursor_name INTO :sno_var, :grade_var;
```

**（4）关闭游标（CLOSE）**

释放游标占用的资源。[01:24]

### 1.2 C语言示例中的游标使用

[00:33] 游标定义了两列（学号、成绩），围绕课程号参数返回对应结果。`FETCH` 后检查 `SQLCODE != 0`：若出错或到达末尾则退出循环。[02:46]

## 二、存储过程

### 2.1 定义与结构

[06:54] 存储过程是部署在服务器端的一段预编译代码，相当于部署在数据库服务器上的一个函数。包含名称、输入参数（IN）、输出参数（OUT），过程体内可使用临时变量、游标、条件分支等。[09:05]

> [09:05] 创建一个存储过程，你就认为是部署在服务器中的一个函数。有函数是不是有名称？存储过程是不是有输入和输出参数，有可能进行参数的传递。

创建语法：

```sql
CREATE PROCEDURE proc_name(IN param1 TYPE, OUT param2 TYPE)
BEGIN
    -- 过程体
    DECLARE var1 TYPE;
    ...
END;
```

调用方式：`CALL proc_name(param1, @result);` [12:11]

### 2.2 学分绩点计算实例

[09:44] 输入参数：学号。输出参数：平均绩点。

过程体内部：[10:34]
1. 声明游标，按学号查出该学生所有课程的成绩
2. 逐行循环：根据每门课成绩按绩点规则转换（90-100 分 → 4.0、80-89 → 3.0 ...）
3. 累加各门课程的绩点
4. 汇总求平均绩点，作为输出参数返回

> [11:51] 里面用到了游标去取某一个学生的所有课程的成绩，然后做一个循环，对每一门成绩进行绩点的转化，最后做一个总的平均输出反馈给客户端。

### 2.3 存储过程的三大优点

**优点一：运行效率高**。[13:27] 存储过程与 DBMS 在同一服务器上集中处理，大数据量计算不通过网络传输原始记录。

> [13:34] 它部署在服务器端，跟DBMS系统集中在一块，大量处理都在服务器端。

**优点二：降低客户机与服务器之间的通讯量**。[13:48] 原来算绩点需要把所有成绩记录拉到客户端逐一计算，现在只传一个学号过去，返回一个绩点值。

**优点三：方便实施企业规则（教师重点强调）**。[14:09]

> [14:13] 如果说一个系统所有这些复杂的业务处理都以存储过程的方式来实现，未来这个逻辑发生改变，我只需要改存储过程，我的程序是可以不变的。

教师举了一个关键场景：[14:59] 在 C/S 架构下，若企业跨国运营，每个客户端都有一套程序。如果业务逻辑写在客户端代码中，规则一变，需要到全球所有地点去更新数百上千个客户端程序，代价极大。而将业务逻辑封装在存储过程中，只须在服务器端更新一次即可。

> [15:28] 如果改服务器上的存储过程，我只要跑到它服务器的这个地方去更新一下存储过程就可以了。

## 四、MVC架构思想

[21:29] 教师指出，任何一个系统本质上包含两大要素：

- **界面交互**：接收用户输入，展示输出结果
- **业务逻辑处理**：对数据做计算、转换、判断

> [22:38] 我们在任何一个系统当中，实际上它包含的要素主要是两大部分，一个是界面，就是把数据输入或把结果输出在屏幕上。第二部分就是所谓的业务逻辑处理。

传统编码往往将两者混在一起（紧密耦合），好的设计应做到松耦合。[23:30] MVC 将程序拆为三层：

- **Model（模型）**：数据处理与业务逻辑
- **View（视图）**：用户界面 / 展示层
- **Controller（控制器）**：接收用户操作，映射到对应的业务逻辑（如点击"添加"按钮 → 调用 INSERT 语句）[24:53]

> [25:30] 如果用Java的一些BS的基本框架，实际上它的整个思路就是基于MVC的方式。

Java 的主流 BS 框架（如 Spring MVC）本质上都遵循 MVC 思路。[25:34]

## 五、数据库存储的出发点

### 5.1 本章在新版教材中的地位

[25:37] 本章是第五版教材新增内容。国内很多国产数据库系统在开源基础上做优化，存储层的优劣在很大程度上决定了 DBMS 好坏。[26:22]

> [26:32] 优化的一个很重要的点，实际上DBMS系统的好与坏，很大的一部分跟存储是紧密相关的。

### 5.2 核心矛盾：空间 vs 时间

[26:48] 数据量越大，I/O 代价越突出。磁盘读写是整个系统最慢的操作，CPU 和内存处理相对快得多。[27:08]

> [27:28] 我指的就是输入输出（I/O），是CPU和计算机对磁盘数据文件的读和写的操作。这个地方是速度最慢的，在内层处理速度还是比较快的。

两大设计目标：[28:01]
1. 提高存储空间效率（尽量节省空间）
2. 提高存取效率（减少读写次数，加快读写速度）

本质是在空间与时间之间做权衡——这与算法设计的经典取舍理念一致。[28:31]

## 六、数据库文件组织与Oracle存储层次

### 6.1 两类文件组织方式

[28:53]

- **方式一**：每个数据库对应一个操作系统文件（早期实现，管理简单但效率不高）[29:13]
- **方式二**：所有数据库对应一个或若干个文件（MySQL、InnoDB 等现代系统的做法，多个表集中在大文件中，效率更高但组织更复杂）[29:23]

### 6.2 Oracle的四级逻辑存储结构

[30:19] Oracle 将数据库存储划分为四级层次：

```
数据库 (Database)
  └── 表空间 (Tablespace)
        └── 段 (Segment)
              └── 区 (Extent)
                    └── 数据块 (Block)
```

- **表空间**：最高逻辑层级，一个物理文件只能属于一个表空间 [32:17]
- **数据块**：I/O 读写的最小单位，通常 512 字节或 1024 字节 [33:03]

MySQL 等系统不显示这么细的层次划分，但其底层也存在类似的数据块概念。[30:58]

## 七、定长记录与变长记录

### 7.1 定长记录（Fixed-length Record）

[32:37] 关系表中每一条元组占据相同大小的字节数。即使字段类型是 `VARCHAR(20)`，也按最大长度 20 分配空间，尽管实际可能只存了 1 个字符。[35:46]

**优点**：[35:14]
- 管理简单：访问第 n 条记录只需 `首地址 + n × 记录长度`
- 增删改操作简单

**缺点**：浪费空间——空值、VARCHAR 未填满的部分都占满空间。[35:07]

另有一些 DBMS 为了让字段地址对齐（如对齐到 4 或 8 字节边界），还会额外填充（padding），进一步浪费空间，但换取了更快的指针访问速度。[37:30]

> [38:26] 有些数据库的定长记录还做了一些优化，它确保某一个数据一定是某一个字节数的倍数，这样便于后续查找属性值。

### 7.2 变长记录（Variable-length Record）

[37:22] 每条记录长度不同，无法通过固定偏移定位。需要额外的长度信息或指针来辅助访问。

> [39:28] 我把一堆的数据连续放在一起，光放数据本身够不够？我取第一列或取第二列，你就不知道从哪边去取了，每个长度不一样。

**三种实现方案：**

**方案一：头部记录总长度 + 每个变长字段前加长度前缀** [40:09]

在记录头部存储该记录的总字节数，每个变长字段前另加一个字段记录该字段实际占用的长度。以额外元数据开销换取变长字段空间的节省。

**方案二：定长字段先行 + 变长字段在后 + 指针** [41:44]

记录的前半部分存放所有定长字段（可直接按类型偏移访问），后半部分存放变长字段，在头部或定长部分之后加指针指向各变长字段的实际位置。[41:56]

**方案三：定长与变长字段分开存储在不同数据块** [42:13]

将定长部分和变长部分（如照片、大文本）存放在不同的数据块中。教师以学生照片为例：

> [43:17] 学生表有学号姓名年龄，假如还有一个照片字段。照片有两种实现方式：一是这一列存储图片文件在服务器上的路径和名称，照片内容并没有存在这张表当中；二是可以把照片的二进制内容（BLOB）直接存入表的这一列——表会急剧膨胀，但读取照片时只需取该字段的值并转换即可。

方案三的分离存储主要应对某些字段数据量极大的场景：当大部分操作不需要访问这些大字段时，分离存储可避免每次读取记录都把所有大字段读进来。[45:14]

### 7.3 定长记录的数据块组织

[46:01] 数据块是固定大小的连续内存空间（如 512 或 1024 字节）。[46:24]

- **新增记录**：追加到块的尾部空闲处，指针后移 [47:15]
- **分配策略**：先申请一个固定大小的块，记录一条条往里放 [48:54]
- 块满了则分配新的数据块 [47:24]

> [49:04] 我先是申请一块空间是一个数据块，固定大小了，然后有一条记录来了就放到这个块里面。记录所占的字节数是固定的，这种管理方式很简单。
