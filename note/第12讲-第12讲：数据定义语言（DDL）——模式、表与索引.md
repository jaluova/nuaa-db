## DDL 概述与层次结构

SQL 中的数据定义语言（DDL）负责数据库对象的创建、修改与删除。其核心操作对象形成一个层次化的逻辑结构：

| 层次 | 对象 | 创建 | 删除 | 修改 |
|------|------|------|------|------|
| 顶层 | 数据库/模式 (Schema) | `CREATE SCHEMA` | `DROP SCHEMA` | 无 ALTER，需删后重建 |
| 中层 | 基本表 (Table) | `CREATE TABLE` | `DROP TABLE` | `ALTER TABLE` |
| 上层 | 视图 (View) | `CREATE VIEW` | `DROP VIEW` | 无 ALTER，需删后重建 |
| 辅助 | 索引 (Index) | `CREATE INDEX` | `DROP INDEX` | 无 ALTER，需删后重建 |

> 数据定义的四类对象中，**只有基本表支持事后修改（ALTER TABLE）**，其余对象若要调整结构，只能删除后重新创建。

## 模式的创建与删除

模式（Schema）定义了一个**命名空间**，相当于创建一个数据库容器。在创建模式时可以同时指定该数据库的管理员用户。

某些 DBMS（如 Oracle）在模式之上还引入了**表空间（Tablespace）**的概念：可以将不同表分配到不同的表空间中，从而在物理层面实现数据的分区部署。例如将部分表空间放置在一台服务器上，另一部分放在另一台服务器上，但对用户而言仍然是一个统一的逻辑数据库。

### 删除模式：CASCADE 与 RESTRICT

删除模式时，如果该模式下存在子对象（表、视图等），DBMS 提供两种处理策略：

| 选项 | 含义 | 行为 |
|------|------|------|
| `CASCADE` | 级联删除 | 删除模式的同时，自动删除其下所有子对象 |
| `RESTRICT` | 限制/拒绝 | 如果模式下存在任何子对象，拒绝删除并返回错误信息 |

> 参照完整性中的级联删除（删除被参照表的记录时自动删除参照表中的对应记录）与模式删除的 CASCADE 是**同一类设计思想**：按照预先定义的规则，由 DBMS 自动完成关联数据的清理，无需应用程序逐条编码。

## 基本表的定义（CREATE TABLE）

创建一张基本表需要定义三方面内容：

1. **表名**
2. **列定义**：每列的名称 + 数据类型
3. **完整性约束**：列级约束与表级约束

### 数据类型

不同 DBMS 对数据类型的支持存在差异，尤其是 MySQL 与 Oracle 之间**字符串类型和日期类型**的兼容性问题最为常见。设计时应尽量选用各系统都兼容的数据类型。

| 类型类别 | 常见类型 | 说明 |
|----------|----------|------|
| 定长字符串 | `CHAR(n)` | 固定分配 n 个字符空间，无论实际存储多长 |
| 变长字符串 | `VARCHAR(n)` | 按实际长度动态调整存储空间，推荐优先使用 |
| 整数 | `INT` / `INTEGER` | 常用整数类型 |
| 浮点数 | `FLOAT` / `DOUBLE` | **涉及金额时切勿使用**，浮点精度误差会导致总账差几分钱 |
| 定点数 | `DECIMAL(p, s)` / `NUMERIC(p, s)` | p 位总长、s 位小数，内部四舍五入，适用于金额 |
| 日期 | `DATE` | 仅年月日 |
| 日期时间 | `DATETIME` / `TIMESTAMP` | 含时分秒，用于登录时间等需要精确到秒的场景 |
| 大文本 | `TEXT` | 存储大量文本（如文档内容） |
| 二进制大对象 | `BLOB` | 存储图片、音频等二进制数据 |

> 用 `FLOAT` 或 `DOUBLE` 存金额是一定会遇到差账问题的——浮点数 0.1 在内部可能是 0.099999……，大量累加后误差就会显现。存钱必须用 `DECIMAL` 这样的定点数类型。

对于图片等二进制数据，有两种存储策略：一是将文件放在服务器指定路径下，表中只存路径字符串；二是直接用 `BLOB` 类型将文件内容存入表中。前者节省表空间但涉及下载和权限问题，后者管理统一但会使表快速膨胀、影响查询性能。

### 完整性约束

| 约束类型 | 作用 | 对应完整性 | 写法位置 |
|----------|------|-----------|----------|
| `PRIMARY KEY` | 标识唯一记录，不允许空值 | 实体完整性 | 单列可写在列定义后；多列联合主键必须写在表级 |
| `FOREIGN KEY ... REFERENCES` | 确保参照关系正确 | 参照完整性 | 表级约束 |
| `UNIQUE` | 确保列值不重复 | 用户自定义完整性 | 列级或表级 |
| `NOT NULL` | 不允许空值 | 用户自定义完整性 | 列级 |
| `CHECK` | 约束取值范围 | 用户自定义完整性 | 列级或表级 |
| `DEFAULT` | 插入时若未提供该列值则使用默认值 | 用户自定义完整性 | 列级 |

> 实体完整性和参照完整性是**必须定义**的，用户自定义完整性则**按需定义**。建表的同时就把数据完整性规则嵌入在表结构中，后续所有数据操作都由 DBMS 自动检查保证——这比写应用程序代码来维护约束可靠得多。

**关于主键写法**：单列主键可以直接在列定义后面写 `PRIMARY KEY`，但如果是多列联合主键，必须将 `PRIMARY KEY(列1, 列2)` 单独作为表级约束写在一行。建议统一使用表级写法，避免混淆。

## 修改基本表（ALTER TABLE）

`ALTER TABLE` 可以在表创建之后进行结构调整，主要包括三类操作：

| 操作 | 语法示意 | 典型场景 |
|------|----------|----------|
| 新增列 | `ADD COLUMN` | 系统升级需要扩展字段 |
| 修改列类型 | `ALTER COLUMN` | 原来定义的宽度不够或类型选错了 |
| 添加/删除约束 | `ADD CONSTRAINT` / `DROP CONSTRAINT` | 初期为方便手工维护数据暂时去掉约束，后期再补上 |

> 实际开发中，有时在系统部署初期会先**去掉参照完整性约束**以方便手工维护数据（否则删除一条记录会因为级联约束而非常麻烦），等数据整理好后再把约束加回去。这是实用技巧，但要确保最终生产环境约束完整。

---

## 删除基本表（DROP TABLE）

与删除模式一致，删除表时也有 `CASCADE` 和 `RESTRICT` 两个选项：

- **CASCADE**：删除表的同时，自动删除在该表上建立的视图、索引、触发器等所有依赖对象。
- **RESTRICT**：如果该表上有任何依赖对象（如视图），DBMS 会返回错误信息，拒绝删除。

> 不同 DBMS 对级联与限制的具体规则存在细微差异，实际使用时需查阅对应系统的文档。

## 索引（INDEX）

索引的目的是**加快查询速度**，其底层通常基于 B+ 树结构。

### 索引的两个关键问题

**索引越多越好吗？** 不是。原因在于：

- 索引本身也是数据块，查询时首先要读取索引块，再通过指针找到数据块。
- 如果表只有一条记录，全表扫描只需读 1 个数据块，而用索引则需要至少读 2 个（索引块 + 数据块），反而更慢。
- 索引还会增加插入、删除、更新操作的开销。

**DBMS 会自动建哪些索引？** 当定义了主键（`PRIMARY KEY`）或唯一约束（`UNIQUE`）时，DBMS 通常会自动在这些列上创建索引，开发者无需重复创建。

### 唯一索引与聚集索引

| 类型 | 特点 | 对物理存储的影响 |
|------|------|-----------------|
| 唯一索引 (UNIQUE INDEX) | 索引列值不可重复 | **不改变**原始记录的物理排列顺序 |
| 聚集索引 (CLUSTERED INDEX) | 按索引列排序 | **会改变**原始记录的物理排列顺序，相同键值的记录在磁盘上连续存放 |

> 聚集索引的核心思想是：让相同索引键值的记录在物理磁盘的同一数据块（或相邻数据块）中。这样一次 I/O 读出一个扇区的数据时，就能把键值相同的所有记录一次性读取到内存，大幅减少磁盘 I/O 次数。

聚集索引的好处在于减少 I/O，但代价是：每当插入新记录或者更新索引键值时，已有序的物理排列需要重新调整，对于频繁更新的列不太适用。因此聚集索引更适合**查询多、更新少**的列。
