## 冗余的辩证认识

数据库管理阶段力求冗余尽可能小，但：

- **冗余不可消灭**——数据之间的关联靠冗余构建（如学号在学生表和成绩表中同时存在）
- **有时需人为增加冗余**——为提升查询效率
  - 如果成绩表只存（学号, 课程编号, 成绩），输出时需关联学生表取姓名
  - 多表关联意味着多次磁盘 I/O，效率低于单表查询
  - 在某些应用场景下，可故意将姓名冗余存入成绩表以提升读取速度
- 冗余的另一代价：**数据不一致**（同一信息在不同地方出现矛盾值）

## 三级模式 · 两级映射

这是 DBMS 实现数据独立性的核心架构。

```
外模式 (External Schema)    ← 用户视图（子模式），面向不同用户的不同子集
    ↕ 外模式 / 模式映射
模式 (Logical Schema)       ← 全局逻辑结构，所有数据对象的完整定义
    ↕ 模式 / 内模式映射
内模式 (Internal Schema)    ← 物理存储结构（文件组织方式、索引等）
```

### 关键结论

| 模式层级 | 数量 | 说明 |
|----------|------|------|
| 外模式 | **多个** | 不同用户看到不同子集 |
| 逻辑模式 | **一个**（关系型 = 二维表） | 全局唯一 |
| 内模式 | **一个** | 物理存储方式唯一，不同 DBMS 互不兼容 |

> MySQL 的数据库文件不能直接被 Oracle 使用，因为两者的**内模式不同**——文件存储结构、组织方式、存放位置均不一致。

### 两级映射如何保证独立性

- **逻辑独立性**：全局表结构改变（如加一列、换列顺序） → 只需修改**外模式/模式映射**，用户程序不变
- **物理独立性**：物理存储方式改变 → 只需修改**模式/内模式映射**，逻辑模式和用户程序均不变

核心机制：**每一层之间通过映射函数隔离变化**。

## 数据模型的三要素

仅定义数据结构（类似画空表）不够，完整的数据模型包含：

| 要素 | 含义 | 性质 |
|------|------|------|
| **数据结构** | 组成对象及对象间的联系（如表的结构定义） | 静态特性描述 |
| **数据操作** | 对数据允许执行的操作（增删改查）及其规则 | 动态特性描述 |
| **完整性约束** | 数据的取值范围、必填限制、表间约束规则 | 静态+动态 |

> 数据结构课定义的"数据结构"只是静态描述，**数据模型 = 数据结构 + 操作 + 约束**。

## 概念模型与 E-R 图

### 从现实世界到机器世界的转换

```
现实世界 → 概念模型（E-R图/需求分析） → 逻辑模型（关系/层次/网状） → 物理模型（DBMS自动完成）
```

- 概念模型：由数据库设计人员将用户需求抽象为信息世界的表达
- 逻辑模型→物理模型：由 **DBMS 自动完成**（设计人员只需选定 DBMS）

### 需求分析中的现实问题

以经典的"秋千图"为例——需求理解在信息传递链中会逐步失真：

> 用户想要的 → 需求人员理解的 → 项目经理设计的 → 程序员实现的 → 销售描述的 → 文档写的 → **最终差异可能很大**

- 初期：信息欠缺（用户无法全面描述需求）
- 后期：信息膨胀（看到原型后不断加需求）
- 好的需求分析人员应**引导和主导用户需求**，而非被动记录

## E-R 图核心概念（考点：每年一题，约10分）

### 四个基本概念

| 概念 | 定义 | 示例 |
|------|------|------|
| **实体 (Entity)** | 客观存在且可相互区分的事物（人/事/物/概念） | 学生、课程、教师 |
| **属性 (Attribute)** | 实体**自身固有**的特性 | 学号、姓名、性别 |
| **码 (Key)** | 能唯一标识一个实体的属性（集） | 学号（单属性码）；学号+课程编号（组合码） |
| **域 (Domain)** | 属性的取值范围 | 0–100（成绩域） |

> 成绩**不是**学生的属性——因为它并非学生自身固有的，而是需要通过选课这一**联系**才能产生。

### 码的判定

给一个属性（集）的值，在表中**最多找到一行** → 该属性集就是码。

以选课登记表（学号, 课程编号, 成绩）为例：
- 学号单独？✗ → 一人选多课，学号对应多行
- 课程编号单独？✗ → 多人选同一课，课程编号对应多行
- **学号 + 课程编号**？✓ → 联合起来唯一确定一行

### 实体间联系（三种）

| 联系类型 | 含义 | E-R 图示例 |
|----------|------|------------|
| **1:1** | 两端各至多对应一条 | 班级 ↔ 班长 |
| **1:N** | 一端对应多条，另一端至多一条 | 班级 → 学生 |
| **M:N** | 两端均可对应多条 | 学生 ↔ 课程 |

#### 具体例子

- **班级 → 班长 (1:1)**：一个班只有一个班长，一个班长只管一个班
- **班级 → 学生 (1:N)**：一个班有多个学生，一个学生只属于一个班
- **学生 ↔ 课程 (M:N)**：一个学生选多门课，一门课被多个学生选
  - M:N 关系通常需要一张**中间表**（选课表）来实现

### E-R 图基本符号

- **矩形**：实体
- **菱形**：联系
- **连线**：连接实体与联系，标注对应关系（1, N, M）

## 选课系统的数据表设计

以选课系统为例，需要三张核心表：

1. **学生表**：学号、姓名、性别、年龄、班级编号
2. **课程表**：课程编号、课程名称、任课教师、学分
3. **选课表**：学号 + 课程编号 + 成绩（组合码）

光有前两张表无法管理选课和成绩——第三张表是 **M:N 联系**的体现。
