## 一、本章要解决的问题

### 如何判定数据库设计的好与坏？

同一个教务系统，不同人可能设计出不同数量的表（1张、2张、3张甚至4张），功能界面看起来差不多——**到底谁的设计更好？**

> [01:10-01:52] 最笨的设计是把所有数据放在一张表里。系统肯定能跑，但设计肯定不好。

### 不良设计的根源

> [02:07-02:37] 不好的设计往往源于**需求分析不到位**。需求做不好 → 设计混乱 → 系统实现不达标，出现大量数据冗余等问题。规范化理论提供了一套**判定好坏的客观方法**，而不是凭感觉。

关键问题：
1. 一个系统应该有几个关系（表）？每个关系包含哪些属性？
2. 表内的属性依赖关系是否合理？
3. 如何判定和改造一个关系模式？

[00:18-04:55]

## 二、关系模式的完整表达

### 关系模式的五元组

关系模式可以形式化表示为：**R(U, D, DOM, F)**

| 符号 | 含义 | 类比 |
|------|------|------|
| R | 关系名 | 表名 |
| U | 属性名集合 | 表的列名集合 |
| D | 所有属性的域（取值范围） | 每一列的数据类型 |
| DOM | 属性到域的映射 | 具体列↔具体数据类型的对应关系 |
| F | 属性间的数据依赖集合 | **本章重点** |

> [05:06-08:20] 手工管理时画一张表：有表名（R），有列名（U），每列有数据类型（D/DOM）。定义数据类型只是给了一个很宽泛的范围，还需要加约束来限制取值。

### 关系模式 vs 关系

| 概念 | 符号 | 含义 |
|------|------|------|
| 关系模式 | 大写的 R | 所有域的笛卡尔积——一个**全集** |
| 关系 | 小写的 r | 全集中去掉无效组合后的**有效数据集合** |

> [16:00-17:30] 关系模式是域的巨大笛卡尔积（全集），里面有很多无效的连接组合。实际的关系（具体数据）是从全集中取出的符合现实约束的那些有效元组。

## 三、函数依赖（Functional Dependency）

### 直观理解

在学生表中，**学号 → 姓名**：
- 给定一个学号，一定能**唯一确定**对应的姓名
- 反过来：给定一个姓名，不一定能唯一确定学号（因为可能有重名）

> [08:21-09:07] 一个关系中属性之间存在依赖关系，学号和姓名之间是有联系的。这种依赖关系**越简单越好**——依赖越简单，说明实体对象抽取得越合理。

### 函数依赖是本章的核心判定工具

- F 是属性间数据依赖的**集合**
- 不同的 F 集合反映了关系模式的"好坏"
- 规范化理论就是以 F 为依据来判定模式是否合理

> [10:00-10:45] 把所有信息塞到一张表里，属性之间的关系就很复杂——这个属性和那个有关系，那个又和另一个有关系，乱七八糟。属性间的依赖关系越简单，设计越合理。

[07:40-12:55]

## 四、不良设计的典型案例

### 把学生、课程、系信息合并成一张大表

设有一个教务关系模式，包含属性：{学号, 所在系, 系主任, 课程名称, 成绩}

| 问题 | 具体表现 |
|------|----------|
| 主键是什么？ | 必须是 **(学号, 课程名称)** 作为联合主键 |
| 冗余大不大？ | 所在系和系主任大量重复存储 |
| 插入异常 | 新生刚报到，还没选课，课程名称为空——主键不能为空，**无法插入** |
| 删除异常 | 把某学生唯一一门课的成绩删除，连系和系主任信息也一并丢失 |
| 更新异常 | 系主任变更需要修改大量记录，可能遗漏导致数据不一致 |

> [18:15-22:05] 学号单独不是主键（一个学生选三门课有三条记录），课程名称单独也不是主键——必须是学号+课程名称联合做主键。实体完整性要求主键不能为空，新生没课程编码时根本插不进去。

### 函数依赖分析

在这个大表中存在如下函数依赖：

| 依赖 | 成立条件 |
|------|----------|
| 学号 → 所在系 | 一个学生只属于一个系 |
| 所在系 → 系主任 | 一个系只有一个系主任 |
| (学号, 课程名称) → 成绩 | 一个学生一门课有一个成绩 |

> [28:53-31:57] 给定学号能确定所在系（不管表中有几条记录，同一个学号的所在系一定相同）。给定所在系能确定系主任。这里依赖关系复杂且交叉，正是坏设计的根源。

[18:10-33:54]

## 五、合理的设计：模式分解

### 正确的实体识别

按照需求分析，应该至少识别出以下实体和联系：

| 实体 | 属性 |
|------|------|
| 学生 | 学号, 姓名, 所在系编号 |
| 系 | 系编号, 系名称, 系主任 |
| 课程 | 课程编号, 课程名称 |

| 联系 | 类型 |
|------|------|
| 选修（学生↔课程） | 多对多，带成绩属性 |
| 隶属（学生↔系） | 多对一 |

> [25:22-27:24] 学生是一个独立实体，系也是一个独立实体——系不会因为某个学生不存在就不存在。学生和系之间是"隶属"联系，学生和课程之间是"选修"联系。至少应有3个以上的关系才算好的设计。

### 分解后的三个关系模式

| 关系 | 属性 | 主键 |
|------|------|------|
| 学生（Student） | 学号, 姓名, 所在系 | 学号 |
| 系（Department） | 系编号, 系名, 系主任 | 系编号 |
| 选课（SC） | 学号, 课程编号, 成绩 | (学号, 课程编号) |

> [39:10-40:10] 分解后，每个关系的函数依赖都变得简单清晰。学生表中学号确定一切，系表中系编号确定一切，选课表中学号+课程编号确定成绩。

### 对应的功能模块

| 功能 | 操作的表 |
|------|----------|
| 学生信息维护 | Student 表（增删改查） |
| 系信息维护 | Department 表 |
| 选课操作 | SC 表 |
| 成绩录入 | SC 表（UPDATE 成绩） |

> [40:22-41:50] 分解后每个功能模块操作的表都独立清晰。学生登记时还需要选择所属的系（下拉选择，数据来自 Department 表），这样就形成了完整的业务闭环。

## 六、关于数据冗余的辩证思考

### 冗余不能也不应完全消除

> [34:55-36:04] 冗余在关键过程当中**不能彻底消除**。学号在 Student 表和 SC 表中都出现——这恰恰是冗余，但**不能去掉**，因为它保证了两个关系之间的数据依赖关系。

### 两个重要原则

| 原则 | 说明 |
|------|------|
| 尽量减少不必要的冗余 | 规范化设计的目标 |
| 可以有意识地增加冗余 | 当某些查询频繁做多表连接时，可人为冗余一些字段来提升性能 |

> [36:04-37:50] 大量使用学号+姓名+课程名称+成绩的组合查询时，如果每次都要三表连接会很慢。此时可以考虑在 SC 表中冗余"姓名"字段——以空间换时间，但要自行保证数据一致性。
