## 数据库安全控制方法回顾

数据库安全控制的五个层次 [09:24]：
1. 用户标识与鉴别（最外层，最基本的用户名/密码）
2. 存取控制（授权机制）

## 自主访问控制（DAC — Discretionary Access Control）

> [14:01] DAC 的安全等级可达 **C2 级别**。如果做到 MAC 则可以达到 **B1 级别**。

### 两个核心命令

| 命令 | 作用 | 记忆方式 |
|------|------|---------|
| `GRANT` | 授予权限 | Grant = 给 |
| `REVOKE` | 回收权限 | Revoke = 收回 |

### 授权的三个要素

授予权限 = **对哪些数据对象** + **有什么操作权限** + **给哪些用户**

### 数据对象的粒度

由粗到细：

| 粒度 | 对象 | 适用场景 |
|------|------|---------|
| 最大 | 数据库 | 权限过大，很少直接授权 |
| 中等 | 表 | 常见，但可能导致并发降低 |
| 较细 | 记录（行） | 行级安全控制 |
| 最细 | 属性列（分量） | 精确控制，如只允许修改某列 |

> [17:38] 粒度**越细越安全**，但**管理代价越大**。原因：
> 1. 授权登记表会变得很大
> 2. 每次操作时DBMS都要查这张表做合法检查，性能必然下降

### GRANT 命令

```sql
GRANT 权限列表
ON 对象名
TO 用户列表
[WITH GRANT OPTION];
```

**WITH GRANT OPTION**：允许被授权者将获得的权限再授予其他用户（权限传递）。

**谁可以执行授权？**
- DBA（数据库管理员）
- 数据库创建者
- 拥有 WITH GRANT OPTION 的用户

### 授权示例

```sql
-- 示例1：将对Student表的查询权限授予用户U1
GRANT SELECT ON Student TO U1;

-- 示例2：将对SC和Student表的所有操作权限授予U2和U3
GRANT ALL PRIVILEGES ON Student, SC TO U2, U3;

-- 示例3：将对SC表的查询权限授予所有用户
GRANT SELECT ON SC TO PUBLIC;

-- 示例4：对Student表学号列的更新权限授予U4（列级授权）
GRANT UPDATE(Sno) ON Student TO U4;

-- 示例5：授予插入权限并允许传递
GRANT INSERT ON SC TO U6 WITH GRANT OPTION;
-- U6可以将此权限再授予U7
```

> [23:16] 执行 `GRANT` 前，数据库中必须**存在该用户**。刚装完的 MySQL 只有 `root`，SQL Server 只有 `sa`，直接执行授予其他用户的命令会失败。

### 权限传递与登记表

```
DBA --GRANT--> U1 --GRANT(WITH GRANT OPTION)--> U2 --GRANT--> U3
```

系统内会维护一张权限登记表，记录所有授权关系。用户越多、粒度越细，这张表越大，权限检查越慢。

### REVOKE 命令

```sql
REVOKE 权限列表
ON 对象名
FROM 用户列表
[CASCADE];
```

| 选项 | 说明 |
|------|------|
| 无 CASCADE | 仅回收该用户的权限 |
| CASCADE | 级联回收——该用户授予他人的权限也一并回收 |

```sql
-- 回收U4对Student表学号列的更新权限
REVOKE UPDATE(Sno) ON Student FROM U4;

-- 回收所有用户对SC表的查询权限
REVOKE SELECT ON SC FROM PUBLIC;

-- 级联回收（U5将其权限传递给了U6、U7，回收U5时一并回收后继）
REVOKE INSERT ON SC FROM U5 CASCADE;
```

> [37:03] 因为 U5 把权限传递给了后面的人，回收 U5 时必须用 CASCADE 级联回收。

## 数据库用户管理

### 创建用户

```sql
CREATE USER 用户名
[WITH DBA | RESOURCE | CONNECT];
```

**三种预定义角色权限对比**：

| 角色 | 创建用户/模式/表 | 登录数据库 | 数据查询操作 |
|------|:---:|:---:|:---:|
| **DBA** | 可以 | 可以 | 可以 |
| **RESOURCE** | 可以 | 可以 | 可以 |
| **CONNECT** | 不可以 | 可以 | 可以 |

> [39:58] 应用系统连接数据库时，不应该直接用超级用户（root/sa）——权限太大，存在安全漏洞。应该创建一个专门的CONNECT级别的连接用户。

### 用户登录验证的实际问题

> [26:34] 应用系统的用户表和数据库用户是两回事：
> - 应用用户表：在数据库中作为一张普通表，存储应用的用户名和密码
> - 数据库用户：是DBMS管理的内置用户，用于数据库连接
>
> 连接数据库时必须以**数据库用户**的身份连接（不是应用表中的用户）。最简单的做法是创建一个低权限的数据库连接用户。

## 数据库角色（Role）

> [40:38] 用户太多时，逐人授权管理太麻烦——类似操作系统的**用户组（group）**概念。数据库角色是**权限的集合**。

### 角色的基本操作

```sql
-- 创建角色
CREATE ROLE R1;

-- 对角色的授权（语法与用户授权相同）
GRANT SELECT, UPDATE, INSERT ON Student TO R1;

-- 将角色授予用户（用户继承角色的所有权限）
GRANT R1 TO U1, U2;

-- 回收角色的权限
REVOKE UPDATE ON Student FROM R1;

-- 从用户回收角色
REVOKE R1 FROM U1;
```

> [41:28] 角色 = 一组权限的集合。用户属于某角色即继承该角色的全部权限。通过对角色授权和回收，能**大幅简化**权限管理的复杂度。

## 强制访问控制（MAC — Mandatory Access Control）

### DAC的局限

DAC 仅控制用户能否操作某个**数据对象**（表/列），没有管**数据内容本身**的安全等级。

> [44:54] 例如：公文中有的公开、有的秘密、有的机密，它们都存在同一张表里。DAC只控制你能不能查这张表，**不管**你能看什么密级的内容——这就可能造成数据的无意泄露。

### MAC 核心概念

| 概念 | 定义 | 标记名称 |
|------|------|---------|
| **主体** | 系统中的活动实体（用户、进程、功能模块） | **许可证级别**（许可密级） |
| **客体** | 被操作的数据对象（文件、表、记录） | **密级**（客体密级） |

**敏感度等级**（从低到高）：公开 < 可信 < 机密 < 绝密

> [48:47] 公文上标注的"秘密""机密"是**客体的密级**；而查看公文的**人**也有对应的**许可证级别**。系统通过匹配主体许可证级别与客体密级来决定访问是否允许。

### MAC 控制规则

系统根据主体许可证级别和客体密级，按预设策略判断是否允许访问——这是 B1 级别安全的核心机制，适用于军队、政府等保密单位的系统。
