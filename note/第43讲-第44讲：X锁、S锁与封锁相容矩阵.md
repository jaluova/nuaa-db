## 并发的基本概念深化

### 并发与冲突的前提

> [16:13] 并发并不是说有多个人去使用这个系统就会产生冲突。我们一般要讲的是——**同一数据对象**。我订的是今天的车票，你订的是明天的车票，虽然我们两个同时操作系统，但是这两个数据对象是不一样的，不会产生并发冲突。

两个关键要素缺一不可：多个事务 + 同一数据对象。

### 三种事务执行方式

**串行执行** [10:27]：事务一个接一个排队执行，上一个提交后才开始下一个。当前时刻只有一个事务在运行，CPU 有大量空闲，但"这是最可靠的一种执行方式——不可能有错" [11:24]。

**交叉并发**（假并发） [11:32]：单核 CPU 将时间片轮流分配给多个事务。给事务 A 一秒钟，切到事务 B 一秒钟，不断交叉轮转——"看起来所有响应都在执行" [12:06]。

> [10:10] 在任何一个时刻，一个单一的 CPU 只能执行一条指令，只能干一件事情。那么存不存在多个程序在同时跑？不存在严格意义上的并行。

> [12:42] 单核 CPU 严格意义上面来讲是不存在真正的并行的。但是这个交叉并发方式比纯粹的串行的好处是减少 CPU 空闲时间——CPU 一直在干活。

**真正并发** [13:46]：多核 CPU 环境下每个核心同时执行不同事务。只有多核才能实现物理上的同时执行。

### 并发调度正确性的根本判据

> [27:31] 判断并发正确的唯一依据是什么？看它的结果——看这个结果是不是跟某一种串行调度的结果是一样的。如果一样，这个并发调度是正确的。

串行执行一定正确，并发执行必须等价于某一种串行执行才正确。这是后续"可串行化"判据的理论基础 [27:42]。

## 三种并发不一致问题的完整梳理

### 数据操作的基本表示

数据库操作归结为两种基本动作 [23:36]：**R**（Read，读操作，即 SELECT）和 **W**（Write，写操作，包括 INSERT、DELETE、UPDATE）。每个事务可以表示为一个 R/W 操作序列。

### 一、丢失修改（Lost Update）

以订票系统为例，剩余票数 A = 16 [18:39]：

时间序列：
1. T1：R(A) = 16
2. T2：R(A) = 16（与 T1 读到相同值）
3. T1：A = A - 1，W(A) = 15（写回）
4. T2：A = A - 1，W(A) = 15（写回，**覆盖了 T1 的修改**）

最终 A = 15，正确结果应为 14。两张票被卖出，但系统只记录卖了一张 [20:32]。

> [21:24] 在并发操作当中，因为第二个事务对 A 的修改覆盖了前面的修改，把它弄丢了。这就是丢失修改。

教师称这种交叉调度是一个"**错误的调度**" [27:05]。

### 二、不可重复读（Non-repeatable Read）

同一事务内，不同时刻读取同一数据对象得到不同值 [22:06]。

以 A = 50、B = 100 为例 [31:02]：
1. T1：R(A) = 50，R(B) = 100，求和 = 150
2. T2：R(B) = 100，B = B × 2 = 200，W(B) = 200
3. T1：再次 R(A) + R(B) = 50 + 200 = 250
4. 同一事务 T1 两次求和结果不一致——B 被 T2 在中间改了

三种子情况 [29:51]：
1. T1 读某数据后，T2 修改该数据并提交，T1 再读时值不同
2. T1 按条件读取一批记录后，T2 插入或删除其中部分记录，T1 再读时记录数变化
3. T1 按条件读取一批记录后，T2 修改了其中某些记录，T1 再读时值变化

> [30:09] 我们一定要保证这个事务当中同一个数据对象在事务中的任何时候，读到的值肯定都是一样的。

### 三、读脏数据（Dirty Read）

[32:27]：
1. T1：R(C) = 100，C = C × 2 = 200，W(C) = 200
2. T2：R(C) = 200（读到了 T1 未提交的中间结果）
3. T1：ROLLBACK（回滚，C 恢复为 100）
4. T2 读到的 200 成为"**脏数据**"——逻辑上不存在的值

> [33:36] T1 做了一个回滚，把 C 撤销到事务之前的状态 100。T2 读到的 200 就称为脏数据，这个数据肯定是不正确的。

核心特征：读到了**未提交事务**的中间结果，该事务随后回滚 [33:37]。

### 冲突分类总结

| 冲突类型 | 示例 | 是否冲突 |
|---------|------|---------|
| R-R（读-读） | T1 读 A，T2 读 A | 不冲突（允许同时读） |
| R-W（读-写） | T1 读 A，T2 写 A | **冲突** |
| W-W（写-写） | T1 写 A，T2 写 A | **冲突** |
| 不同数据对象 | T1 对 A 操作，T2 对 B 操作 | 不冲突 |

> [28:55] 唯一冲突的就是对同一个数据对象的读和写的操作。读与读之间有些情况下是允许的。

### 问题的本质

三种不一致问题本质上都是并发调度**破坏了事务的隔离性**（Isolation，ACID 中的 I）[34:02]。事务之间理应相互隔离，一个事务的执行不应影响其他事务的结果。

> [34:16] 事务是隔离的。事务相互之间的执行不应该影响其他事务的运行结果，任何时候都不影响。

## 封锁机制（Locking）

### 封锁的基本概念

封锁是并发控制的核心手段 [35:23]。事务在操作数据对象之前，先向 DBMS 发出封锁申请，获得授权后才能执行操作。

> [35:42] 所谓封锁就是所有的事务向 DBMS 系统申请对数据对象的使用权限。对数据对象操作之前，先向系统发出请求——加锁。加锁以后事务就对数据对象有一定的控制，在他释放之前，其他事务不能更新这个数据对象。

基本工作流程 [36:03]：
1. 事务需要操作数据对象 A
2. 向 DBMS 系统申请对 A 的锁（X 锁或 S 锁，取决于操作是写还是读）
3. DBMS 查询内部锁表，检查当前 A 的锁状态
4. 若相容 $$\\to$$ 授予锁，事务执行操作
5. 若不相容 $$\\to$$ 事务进入**等待队列**，直到持有者释放锁

> [39:50] DBMS 系统逻辑上有一个很大的一张表，当前正在运行的每一个事务对哪个数据对象加了什么锁，都记下来。其他事务申请操作的时候要去查那张表。

### 排他锁（X 锁 / Exclusive Lock / 写锁）

> [38:02] 某一个事务 T 对数据对象 A 加上了 X 锁，则只允许 T **读取和修改** A。其他任何事务都不能够对 A 加**任何类型**的锁，直到 T 释放它为止。

持有 X 锁后 [38:36]：
- 持有者可以**读**和**写**该数据对象
- 其他事务**连读都不能读**——完全排他访问

教师用订票类比 [35:55]：我去订某个座位的票，向系统申请对这个座位数据对象的 X 锁。在我操作完成并释放锁之前，谁也操作不了这个座位。

### 共享锁（S 锁 / Shared Lock / 读锁）

> [40:43] 事务 T 对数据对象 A 加上 S 锁，则其他事务只能对 A 加 **S 锁**，不能加 X 锁。也就是不能改——大家同时去读可以，但是不能写。

持有 S 锁后 [41:06]：
- 持有者可以**读**
- 其他事务可以加 S 锁（同时读）
- 不能加 X 锁（不能写）

教师强调：S 锁保证了"共享读、排他写"的策略 [41:35]。

### 锁类型判断规则

> [47:43] 看事务对数据对象执行的是**读的操作**还是**写的操作**。如果是读的操作，申请 S 锁。如果是写的操作（INSERT、DELETE、UPDATE），申请 X 锁。

## 锁相容矩阵——考试核心

锁相容矩阵规定了事务申请锁时是否与数据对象上已有的锁冲突 [42:30]：

|  | 已加 X 锁 | 已加 S 锁 |
|--|---------|---------|
| 申请 X 锁 | **不兼容**（等待） | **不兼容**（等待） |
| 申请 S 锁 | **不兼容**（等待） | **兼容**（可加） |

> [42:33] 申请了 X 锁，其他事务再申请 X 锁能不能得到满足？不能。申请 S 锁也不能——是不是都不能？然后这边申请 X 锁肯定不满足，申请 S 锁是可以满足要求的。

**记忆要点**：四种组合中，只有 **S + S 兼容**（两个事务同时申请读锁可以共存），其余三种组合均不兼容。

## 封锁如何解决三种并发问题

教师用三个带锁的图示做详细分析 [43:23]。

### 场景一：解决丢失修改

T1 对 A 执行写操作，申请 **X 锁** $$\\to$$ 获得锁 $$\\to$$ 执行 R(A)、计算 A-1、W(A) [43:42]。

T2 也对 A 执行写操作，也要申请 X 锁 $$\\to$$ 但 T1 持有 X 锁未释放 $$\\to$$ **T2 等待**。

T1 完成后释放 X 锁 $$\\to$$ T2 获得 X 锁 $$\\to$$ 执行 R(A)=15、计算 A-1、W(A)=14。

> [45:39] 因为对锁的申请，事实上保证了这两个事务是按照串行执行的方式往下执行的。丢失修改问题肯定就不存在了。最终结果 14 正确。

实际效果：两事务从交叉并发变为事实上的串行执行。

### 场景二：解决不可重复读

T1 对 A、B 只需要读操作 $$\\to$$ 申请 **S 锁** $$\\to$$ 获得 S 锁 $$\\to$$ 执行 R(A)、R(B) [46:35]。

T2 要对 B 执行写操作 $$\\to$$ 申请 **X 锁** $$\\to$$ 但 T1 持有 B 的 S 锁 $$\\to$$ **T2 等待**。

T1 完成求和后释放 S 锁 $$\\to$$ T2 获得 X 锁 $$\\to$$ 修改 B。

> [48:19] 申请了 S 锁，其他事务只能再申请 S 锁，不能申请 X 锁。所以 T2 的请求得不到满足，只能等待。T1 读到的 A、B 的值肯定都是同一个值。

T1 的两次求和都在同一个事务内得到一致结果 150——不可重复读被消除。

### 场景三：解决读脏数据

T1 要对 C 执行写操作 $$\\to$$ 申请 **X 锁** $$\\to$$ 获得锁 $$\\to$$ 修改 C = 100 $$\\to$$ 200 [49:14]。

T2 想读 C $$\\to$$ 申请 S 锁 $$\\to$$ 但 T1 持有 X 锁 $$\\to$$ **T2 等待**。

T1 随后 ROLLBACK（C 恢复为 100）$$\\to$$ 释放 X 锁 $$\\to$$ T2 获得 S 锁 $$\\to$$ 读到 C = 100。

> [49:54] T2 到这里为止，申请 S 锁得不到满足。因为 T1 持有 X 锁。T2 只能等 T1 释放以后才能读，此时读到的是回滚后的 100。

关键：T2 永远不可能在 T1 释放 X 锁之前读到 C，因此绝对读不到 T1 未提交的中间值——脏读被彻底消除。

## 封锁机制总结

封锁的核心思想是：通过锁的**申请—等待—释放**机制，将交叉并发的事实执行序列**转化为等价于某种串行执行序列** [45:55]。串行是一定正确的，因此封锁能保证并发调度的正确性。
