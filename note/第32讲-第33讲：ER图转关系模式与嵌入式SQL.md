## 一、ER图向关系模式的转换规则

上一章讲完需求分析之后，逻辑设计阶段的核心任务就是把ER图转换成关系模型。[02:26] 教师以科室-医生的经典例子，逐条推演了三种联系类型所对应的表数量设计决策。

> [03:36] 那么我们以一个简单的例子给大家来看一下，就是说我们讲这是科室，这是医生，这个地方有个属于是不是这样的一个联系对吧？那么我们就以这个例子来看一下，我们在这样的一个ER图以后，我们为了创建表的时候是创建几张表，所以这里面大家可以看一下，这边有三条规则。

### 1.1 一对一的联系（1:1）

语义：一个医生只能在一个科室工作，一个科室只有一个医生。[04:28]

理论上可以设计三张表（科室表、医生表、联系表），但三张表做连接查询代价大。[06:50] 实际做法是将联系合并到任意一端的关系模式中——在医生表加 `kid` 字段，或在科室表加 `did` 字段。[07:38]

> [08:00] 理论上来讲，是不是可以加到任何一端，也就是说我理论上来讲，也就是这张表我们是理论上可以取消的，这个关系是不是可以直接在任何两端的任何一张表里面增加。

甚至在某些极端情况下，若两表的字段均不多，可合并为一张表。[08:28] 决策关键：两边表的大小。若医生表有 50 列而科室表仅 2~3 列，合并会影响空间利用率，但好处是查询时不再需要表连接。[08:51]

**结论**：一般 2 张表（极少 1 张或 3 张）。[09:24]

### 1.2 一对多的联系（1:N）

语义：一个科室有多个医生，一个医生只属于一个科室。[09:51]

核心规则：联系只能合并到 **N 端**（医生表），不能合并到 1 端（科室表）。[10:10] 原因：一个科室对应多个医生，在科室表里加医生 ID 无法容纳多个值。[10:23]

> [10:44] 如果变成两张表的话，科室是一张表，然后医生是一张表，但是他把他这两个之间的联系的科室的ID号是不是放在医生里了，是不是设计两张表了？

**结论**：2 张表（也可 3 张表，但一般 2 张）。[10:55]

### 1.3 多对多的联系（M:N）

联系无法合并到任何一端——无论放哪一端都会出现多值问题。[11:24] 因此联系表**必须保留**，最少 3 张表。[11:33]

> [11:57] 大家注意一下，就是说你们后面写实验报告的时候，注意一下你画出来的ER图实际上是不是跟你的表设计有一个对应关系。简简单单的两个实体加一个联系，它有可能是一张表，有可能是两张表，有可能是三张表。

**表设计决策总结：**

| 联系类型 | 最少表数 | 说明 |
|---------|--------|------|
| 1:1 | 2 张 | 联系可合并到任意一端 |
| 1:N | 2 张 | 联系只能合并到 N 端 |
| M:N | 3 张 | 联系无法合并，必须独立 |

## 二、嵌入式SQL的基本概念

### 2.1 两种使用场景

[12:13] SQL 的使用方式分为两类：

- **交互式 SQL**：用户在 DBMS 客户端直接输入 SQL 命令并立即获得结果。这种方式不适用于最终用户系统。[12:59]
- **嵌入式 SQL**：在高级语言（Python、Java、C#、C++ 等）代码中嵌入 SQL 语句，通过图形化界面与用户交互，SQL 提交给 DBMS 后端执行。[13:15]

> [13:11] 肯定不现实。一定是提供一个界面给用户使用，但是当你这个界面里面是不是要跟后台的数据库去打交道，是不是要调用一些SQL语句？这样的一个使用方式就叫嵌入式的使用场景。

### 2.2 SQL与高级语言的核心矛盾

[16:25] SQL 是面向集合的——一次 `SELECT` 返回一个二维结果集；而高级语言是面向记录的——逐行处理。解决方式是将结果集映射到二维数组或类似结构，再逐行展示。[17:04]

### 2.3 通讯机制三要素

前端程序与 DBMS 是两个独立进程，需要信息交互来获知 SQL 执行是否成功。[17:54] 为此引入了三个关键概念：

**通讯区（SQLCA）**：前端与 DBMS 共享的一个结构体变量，最重要的分量是 `SQLCODE`，用于判断当前 SQL 语句执行成功或失败。[18:36] `SQLCODE != 0` 表示出错，后续业务逻辑应终止并做错误处理。[19:28]

> [19:17] 你在前端的语言当中可以根据什么状态信息来控制程序的代码执行。大家如果我传一条命令让你执行，你执行都失败了，后续的业务处理还能不能继续？就不能继续下去了。

**主变量（Host Variable）**：前端和 DBMS 共享的全局变量，用于传递单个值（如学号、密码）。[19:46]

**游标（Cursor）**：用于处理多条记录。游标本质上是对查询结果集设置一个行指针，从第一行开始逐行读取，读完一行后指针下移，直到遍历完全部记录。[20:38]

> [20:44] 游标是不是对这个结果集有个指针，指针指向某一行，然后这一行处理结束以后，是不是把指针指向下一行？这个就称为游标的指针。

## 五、CTE 与递归查询

### 5.1 CTE（Common Table Expression）

[29:50] CTE 通过 `WITH` 子句定义临时结果集，在一条 SQL 语句执行过程中有效。其核心思想是：先将满足条件的数据查出存入一个临时表，外层查询直接在该临时表上操作，实际分两步完成。[32:40]

**CTE vs 传统表变量**：CTE 效率更高，适合大数据量。表变量本质也是临时表，但增加额外的 I/O 开销。[33:03]

> [34:34] 这种CTE的表示方式是比变量表的效率要高得多的。

[34:42] CTE 实例——求两个教学班学生平均成绩的差异：

```sql
WITH class1_avg(avg_score) AS (
    SELECT AVG(score) FROM sc WHERE cno = '8101-1'
),
class2_avg(avg_score) AS (
    SELECT AVG(score) FROM sc WHERE cno = '8101-2'
)
SELECT class1_avg.avg_score - class2_avg.avg_score
FROM class1_avg, class2_avg;
```

先用两条子查询分别求出两个班级的平均成绩放入临时表，再做减法。

### 5.2 递归 CTE（WITH RECURSIVE）

[38:44] 递归 CTE 由三部分组成：

1. **种子查询**（初始数据，不引用 CTE 自身）
2. **`UNION ALL`**
3. **递归部分**（引用 CTE 自身，从种子结果集出发逐层扩展）

```sql
WITH RECURSIVE cte_name(col1, col2) AS (
    -- 种子查询
    SELECT ... WHERE ...
    UNION ALL
    -- 递归部分
    SELECT ... FROM table JOIN cte_name ON ...
)
SELECT * FROM cte_name;
```

### 5.3 案例一：查询"数据库系统概论"的所有先修课程

[39:40] 课程表包含课程编号、课程名称、先修课程编号。课程之间形成层次关系。

- 种子查询：根据"数据库系统概论"的课程名称查其直接先修课程编号
- 递归部分：从已找到的课程编号出发，继续查找它们的先修课程
- 外层 SELECT：将递归得到的编号集合与课程表做连接，获取完整的课程信息

> [40:57] 第一条SQL语句根据这个课程名称查到先修课程编号，这是种子。第二条语句根据这个编号去递归查，根据这个号查这个号对应的先修课。这两条命令操作是不一样的。

注意：递归结束后得到的只是课程编号的集合，最后仍需与课程表连接获取完整信息（课程名称、学分等）。[46:42]

### 5.4 案例二：系统菜单层次结构递归输出

[43:10] 某系统的功能菜单登记表中，主菜单 `parent_id = NULL`，子菜单的 `parent_id` 指向父菜单编号。

- 种子查询：`WHERE parent_id IS NULL` 找出第一层菜单
- 递归部分：从模块表中 `SELECT ... WHERE parent_id = 当前节点的模块编号`

> [46:42] 简简单单的这么几条语句我就可以得到这个结果。否则的话你递归程序是不是要写一堆。

用递归 CTE 替代高级语言中的大量递归/循环代码，且多次反复读写表的效率远不及 CTE 一条 SQL。[46:57]

### 5.5 案例三：日期函数与一周内过生日查询

[47:22] 核心思路：获取当前系统日期的 4 位年份（格式 `%Y`），与出生日期的月、日拼接成字符串，再转换为日期类型，判断是否在当前日期起一周范围内。[48:28]

不同 DBMS（MySQL、SQL Server、Oracle）的内嵌函数（日期函数、数学函数、字符串函数）名称和用法有差异，实际使用时需要查阅对应文档。[47:44]
