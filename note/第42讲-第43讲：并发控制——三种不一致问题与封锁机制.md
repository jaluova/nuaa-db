## 系统故障恢复算法复习

教师首先回顾系统故障恢复算法 [00:50]。核心步骤：

1. **正向扫描日志文件**，将事务分类
2. 有 BEGIN 且有 COMMIT $$\\to$$ **REDO 队列**（已完成但数据可能未写入磁盘）
3. 有 BEGIN 但无 COMMIT $$\\to$$ **UNDO 队列**（未完成但可能已修改数据）
4. 先执行 UNDO（反向扫描做逆操作），再执行 REDO（正向扫描重新执行）

> [03:22] 在日志当中已经出现它有开始有结束了，但是它数据还在缓冲区里面，操作系统正在往磁盘逻辑上面写的时候，这个时候出了问题。没有真实反映到磁盘文件上面。

以教材第 331 页第 4 题为例：T1、T2、T3（有 COMMIT $$\\to$$ REDO 队列），T4（只有 BEGIN 无结束记录 $$\\to$$ UNDO 队列）。教师明确指出："这个是我们未来考试的一个最基本的要求" [08:58]。

## 介质故障恢复流程

介质故障（硬盘损坏）的恢复前提 [09:15]：

> [09:33] 它的备份不能坏，还有一个哪个东西不能坏——日志文件不能坏。备份文件是好的，日志文件也是正常的，这两种前提下才能谈得上恢复。

恢复步骤 [10:42]：
1. **装入最新的数据库后备副本** $$\\to$$ 恢复到备份时刻的一致性状态
2. 对于**静态备份**：直接利用日志文件将备份后到故障前的已完成事务 REDO，未完成事务 UNDO
3. 对于**动态备份**：需额外处理备份期间的事务（结合系统故障恢复方法做 UNDO/REDO）

## 检查点（Checkpoint）机制

### 为什么需要检查点

每次故障都扫描全部日志文件代价过大。当系统运行多年后，日志文件极其庞大，全量扫描+全量 REDO 耗时太长 [22:00]。

> [22:00] 出了问题每次都去把日志文件从头到尾扫描一遍，这个代价太大。所有 REDO 操作涉及数据的重新修改，重新 IO 读写，会耗大量的时间。

### 检查点的原理

类比 Windows 还原点或 Word 的自动保存与逐步回退功能 [23:00]。

**检查点记录的内容** [24:37]：当前时刻所有正在执行的事务清单，以及指向这些事务日志记录的指针。

**重新开始文件**（Restart File）：与日志文件配合的索引文件，记录各检查点记录在日志文件中的地址。恢复时先查这个文件找到最新检查点 [23:55]。

### 建立检查点的四个步骤

由 DBMS 自动完成 [32:29]：

> [32:51] 第一步：将当前日志缓冲区的所有日志记录写入磁盘日志文件。第二步：在日志文件中写入一条检查点记录。第三步：将当前数据缓冲区的所有数据强制写入磁盘数据文件——解决的是确保检查点之前已完成事务的数据真实反映在磁盘上。第四步：在重新开始文件中记录该检查点记录的地址。

注意：先写日志再写数据——日志文件永远优先。

### 基于检查点的恢复算法

> [43:52] 先做两个队列，一个是 UNDO 队列，一个是 REDO 队列。先把当前正在运行的事务清单（检查点记录中的）默认放在 UNDO 队列当中——先默认它是未完成的。

算法步骤 [44:45]：
1. 从重新开始文件找到**最新检查点记录**
2. 将该检查点时刻的活动事务清单全部放入 **UNDO 队列**
3. 从检查点开始**正向扫描**日志文件
4. 遇到新事务 BEGIN $$\\to$$ 加入 UNDO 队列
5. 遇到某事务 COMMIT $$\\to$$ 从 UNDO 队列移至 REDO 队列
6. 扫描结束后，先对 UNDO 队列执行 UNDO，再对 REDO 队列执行 REDO

**多个检查点的处理**：只关心最新检查点，更早的检查点及其之前的所有事务一概不管 [38:26]。

## 磁盘镜像与读写分离

作为数据库恢复章的收尾内容 [46:34]。

**磁盘镜像**：将数据库同步复制到另一个磁盘/服务器上，主数据库和镜像数据库逻辑上为一个整体。

> [47:52] 在一个数据库管理当中，80% 的是查询，20% 的操作是数据的更新。如果查询和更新都是对同一个服务器同一个磁盘去进行 IO 操作的话，当用户数量增加，IO 的瓶颈很明显。

**读写分离**（Read-Write Separation）[47:44]：
- 写操作指向主数据库（Master）
- 读操作分流到镜像数据库（Slave）
- 有效降低主库 IO 负载，提升并发性能
- 主库故障时可自动切换到镜像库

这是典型的 Master-Slave 架构，两个数据库逻辑上一致，物理上可部署在同一台机器的不同磁盘上，也可部署在不同物理机器上 [01:21]。

> [02:42] 这就是下一章要给大家讲的并发处理的问题——并发用户数多了以后，怎样保证系统性能。

## 并发控制概述

### 什么是并发

并发即允许多个用户同时使用数据库。核心问题是：多个事务对**同一数据对象**的操作冲突 [06:56]。

> [16:13] 并发的冲突并不是说有多个人去使用这个系统就会产生。我们一般要讲的是——**同一数据对象**。我订的是今天的车票，你订的是明天的车票，虽然我们两个同时操作系统，但是这两个数据对象是不一样的，不会产生并发冲突。

### 三种事务执行方式

| 方式 | 特点 | 可靠性 | 效率 |
|-----|------|-------|------|
| **串行执行** | 事务一个接一个，上一个结束下一个才开始 | 完全正确 | CPU 空闲多 |
| **交叉并发**（假并发） | 单核 CPU 画时间片轮转执行，看起来"同时" | 可能出错 | CPU 利用率高 |
| **真正并发** | 多核 CPU 每个核心同时执行不同事务 | 可能出错 | 效率最高 |

> [10:13] 在任何一个时刻，一个单一的 CPU 只能干一件事情。多个程序"同时跑"是通过时间片轮转——给你跑一秒钟，给他跑一秒钟，不断交叉。看起来所有响应都在执行。

在单核 CPU 环境下不存在严格意义上的真正并行，只能是**交叉并发**。多核 CPU 环境下才存在多个事务在物理上同时执行 [13:46]。

### 并发调度正确性的判据

> [27:31] 判断并发正确的唯一依据是什么？就看它的结果。看这个结果是不是跟某一种串行调度的结果是一样的。如果是，我认为这个并发调度是正确的。

如果一个并发调度的最终结果，与某一种串行调度的结果相同，则该并发调度是正确的。反之错误。**串行执行一定正确，因为一个事务做完下一个再做，不存在相互干扰。**

## 并发引发的三种数据不一致问题

### 数据操作的基本表述

数据库操作归结为两种基本动作：**R**（读操作，Read）和 **W**（写操作，Write，包括 INSERT、DELETE、UPDATE）。后续分析均以 R 和 W 的序列来表示事务的执行过程。

### 一、丢失修改（Lost Update）

典型案例——订票系统 [16:53]：

设剩余票数 A = 16：
- $$t_1$$：T1 读 A = 16
- $$t_2$$：T2 读 A = 16（此时 T1 尚未写回）
- $$t_3$$：T1 计算 A - 1 = 15，写回
- $$t_4$$：T2 计算 A - 1 = 15，写回

最终数据库中 A = 15，而正确结果应为 14（卖出两张票）。

> [20:27] 如果处理不好，可能卖了两张票，最后系统里面显示只少了一张票。

本质：T2 的写入**覆盖**了 T1 的修改 [21:57]。

### 二、不可重复读（Non-repeatable Read）

同一事务内两次读取同一数据值不同，因为其他事务在中间修改了该数据 [22:02]。

教师以 A = 50，B = 100 场景举例 [31:02]：
- T1 第一次读 A + B = 150
- T2 将 B 改为 200 并提交
- T1 第二次读 A + B = 250
- 同一事务内两次的结果不同

三种子情况 [29:51]：
1. T1 读数据后 T2 修改该数据并提交，T1 再次读时值已变化
2. T1 按条件读取一批记录后，T2 插入/删除了其中部分记录，T1 再次读时记录数变化
3. T1 按条件读取一批记录后，T2 修改了其中某些记录，T1 再次读时值变化

### 三、读脏数据（Dirty Read）

> [32:27] T1 读 C = 100，乘以 2 得 200 写回。T2 读到 C = 200。T1 做了一个回滚 ROLLBACK——把 C 撤销到事务执行前的状态 100。T2 读到的 200 就称为脏数据。

核心特征：读到了其他事务修改后**尚未提交**的中间结果，而该事务随后回滚 [32:50]。

### 冲突类型分析

对同一数据对象的操作冲突只存在于两种情况 [28:22]：

- **读写冲突**（R-W）：一个事务读，另一个事务写
- **写写冲突**（W-W）：两个事务同时写
- **读读不冲突**（R-R）：允许同时读

不同数据对象之间不存在任何冲突。

> [28:45] 唯一冲突的就是对同一个数据对象的读和写的操作。读与读之间有些情况下是允许的。

### 问题的本质

三种不一致问题本质上都是不正确的并发调度**破坏了事务的隔离性**（Isolation，ACID 中的 I）[34:02]。事务之间理应相互隔离，互不影响。

## 封锁（Locking）机制

解决并发问题的核心手段是**封锁**——事务在操作数据对象前，先向 DBMS 申请对该数据对象的锁，获得授权后才能进行操作 [35:23]。

基本工作流程 [35:58]：
1. 事务在执行读写操作前，向 DBMS 发出封锁申请
2. DBMS 检查该数据对象当前的锁状态（查内部锁表）
3. 若申请与现有锁相容 $$\\to$$ 授予锁，事务继续执行
4. 若不相容 $$\\to$$ 事务进入等待队列

> [39:50] DBMS 系统逻辑上有一个很大的一张表，当前正在运行的每一个事务对哪个数据对象加了什么锁，都记下来。其他事务申请操作的时候要去查那张表。

### 排他锁（X 锁 / Exclusive Lock / 写锁）

> [38:02] 某一个事务 T 对数据对象 A 加上了 X 锁，那么则只允许 T 读取和修改 A。其他任何事务都不能够对 A 加任何类型的锁，直到 T 释放它为止。

持有 X 锁后：允许 **读** 和 **写**。其他事务不能加**任何**类型的锁（连 S 锁也不行）——完全独占 [38:21]。

### 共享锁（S 锁 / Shared Lock / 读锁）

> [40:43] 事务 T 对数据对象 A 加上 S 锁，则其他事务只能对 A 加 S 锁，不能加 X 锁。也就是不能改——大家同时去读可以，但是你不能改。

持有 S 锁后：允许 **读**。其他事务只能再加 S 锁（可同时读），不能加 X 锁（不能写）[41:23]。

### 锁相容矩阵——核心规则，必须记牢

|  | 已加 X 锁 | 已加 S 锁 |
|--|---------|---------|
| 申请 X 锁 | 不兼容（等待） | 不兼容（等待） |
| 申请 S 锁 | 不兼容（等待） | **兼容**（可加） |

> [42:33] 申请了 X 锁，其他事务申请 X 锁能不能得到满足？不能。申请 S 锁也不能。只有 S+S 兼容。

判断规则很简单：看事务对数据对象执行的是**读**还是**写**。读操作申请 S 锁，写操作（增删改）申请 X 锁 [47:43]。

## 封锁如何解决三种并发问题

教师用三个带锁标注的执行序列图分别演示：

**解决丢失修改** [43:08]：T1 对 A 申请 X 锁并获准 $$\\to$$ 执行 R(A)、修改、W(A)；T2 试图对 A 申请 X 锁 $$\\to$$ 冲突等待；T1 释放锁后 T2 获得锁。实际效果：两事务串行执行，结果 16 $$\\to$$ 15 $$\\to$$ 14 正确。

**解决不可重复读** [46:35]：T1 对 A、B 申请 S 锁（只读）；T2 想修改 B 需申请 X 锁 $$\\to$$ 与 T1 的 S 锁冲突，T2 等待；T1 完成求和后释放 S 锁。T1 读到的始终是一致数据。

**解决读脏数据** [49:14]：T1 对 C 申请 X 锁（要写），修改 C = 100 $$\\to$$ 200；T2 想读 C 申请 S 锁 $$\\to$$ 与 T1 的 X 锁冲突，T2 等待；T1 ROLLBACK 后释放锁，T2 获得 S 锁读到 C = 100。脏读被消除——T2 永远不可能读到未提交的中间数据。

> [45:39] 因为对锁的申请，事实上保证了这两个事务是按照串行执行的方式往下执行的。丢失修改问题肯定就不存在了。

**核心结论**：封锁使并发调度事实上的执行序列**等价于某种串行执行序列**，从而保证了数据的正确性。
