## 一、触发器的基本概念

### 什么是触发器

触发器是一种**特殊的代码**，部署在 DBMS **服务器端**，由服务器根据预设的事件**自动激活**执行。

> [01:06-02:10] 不管系统是什么功能，最终归根到底就是对表的增删改查。当某段程序对某张表进行数据操作时，可以在后台自动触发一段代码的运行——这就是触发器。

触发器的三个特点：

| 特点 | 说明 |
|------|------|
| 服务器自动激活 | 由 DBMS 根据设定的事件自动执行，不依赖前端代码 |
| 可进行复杂检查 | 支持循环、分支、顺序处理等结构化编程逻辑 |
| 部署在数据库端 | 不用修改客户端程序，触发逻辑集中在服务器 |

## 二、触发器的语法结构

### 基本语法

```sql
CREATE TRIGGER trigger_name
{BEFORE | AFTER} {INSERT | DELETE | UPDATE [OF column]}
ON table_name
[FOR EACH {ROW | STATEMENT}]
[WHEN (condition)]
BEGIN
    -- 触发器代码体
END;
```

### 关键要素解析

| 要素 | 选项 | 说明 |
|------|------|------|
| 触发时机 | BEFORE / AFTER | 在SQL语句执行**之前**还是**之后**触发 |
| 触发事件 | INSERT / DELETE / UPDATE | 主要针对数据的增、删、改操作（查询一般不需要触发器） |
| 粒度 | FOR EACH ROW / STATEMENT | 行级触发 vs 语句级触发 |
| 触发条件 | WHEN | 满足条件时才执行触发器体 |

> [05:20-06:55] 查询（SELECT）操作一般不需要触发器，触发器的应用场景主要是在**增删改**这些数据更新操作上。

### FOR EACH ROW 与 FOR EACH STATEMENT 的区别

| 类型 | 执行次数 | 场景 |
|------|----------|------|
| FOR EACH STATEMENT（语句级） | 整个SQL语句只触发**一次** | 无论影响了多少行，触发器代码只执行一遍 |
| FOR EACH ROW（行级） | 每影响一行触发**一次** | 影响了N条记录，触发器代码就执行N遍 |

**例子：** `UPDATE teacher SET dept=5 WHERE dept=3` 影响了1000条记录：
- 如果是**语句级**触发器：触发1次
- 如果是**行级**触发器：触发1000次

> [08:12-10:00] 如果一条 UPDATE 涉及10个学生的成绩修改，行级触发器就执行10次——每更改一行，触发器代码就执行一遍。

## 三、触发器实例

### 例1：数据合规性检查（BEFORE 触发器）

**场景：** 新增教师时，检查工资是否在合理范围内（如教授工资不低于4000），若不合法则自动修正。

```sql
CREATE TRIGGER check_salary
BEFORE INSERT OR UPDATE ON teacher
FOR EACH ROW
BEGIN
    IF :NEW.title = '教授' AND :NEW.salary < 4000 THEN
        :NEW.salary := 4000;
    END IF;
END;
```

关键对象：
- **:NEW**：代表当前新插入或更新后的记录
- **:OLD**：代表更新前的旧记录（仅在 UPDATE 和 DELETE 中有效）

> [20:40-23:30] 触发器部署在服务器端，未来业务规则变化时，只需修改触发器代码，**客户端程序不需要做任何改动**——这就实现了业务规则与客户端的解耦。

### 例2：工资变动流水记录（AFTER 触发器）

**场景：** 建立一张工资变动流水表（salary_log），当教师工资发生变更时，自动记录变动明细。

```sql
CREATE TRIGGER log_salary_change
AFTER UPDATE ON teacher
FOR EACH ROW
BEGIN
    IF :NEW.salary <> :OLD.salary THEN
        INSERT INTO salary_log(teacher_id, old_salary, new_salary, change_date)
        VALUES (:OLD.id, :OLD.salary, :NEW.salary, SYSDATE);
    END IF;
END;
```

> [28:00-30:55] 这个例子展示了触发器的"打补丁"能力——假设系统已经部署运行，用户突然提出要记录工资变动流水。你不需要改动原有程序，只需在服务器端：**新增一张日志表 + 定义一个 AFTER 触发器**，功能就扩展完成了。

## 四、BEFORE 与 AFTER 的典型用途

| 时机 | 典型用途 | 说明 |
|------|----------|------|
| BEFORE | 数据合规性检查 | 在数据写入之前验证、修正数据 |
| AFTER | 善后处理 / 功能扩展 | 操作成功后记录日志、同步数据、打补丁 |

> [34:00-34:55] BEFORE 触发器做前处理（验证），AFTER 触发器做善后处理（日志、同步）。这个时间点直接决定了你是"拦路检查"还是"事后记账"。

## 五、触发器的执行顺序

当一条 DML 语句提交后，DBMS 的实际执行顺序：

```
执行所有 BEFORE 触发器
  → 执行 DML 语句本身
    → 执行所有 AFTER 触发器
```

> [38:35-41:05] 一张表上可以定义多个触发器。先执行所有 BEFORE 触发器，然后执行 SQL 本身，最后执行所有 AFTER 触发器。如果任一触发器出错，**整个操作都会失败**——原来的正常操作也会受到影响。

**注意事项：**
- 触发器代码写得不好，会导致原本正常的系统跑不起来
- 给现有系统"打补丁"时，必须保证触发器的正确性

## 六、触发器的实战价值

### 应用场景

| 场景 | 说明 |
|------|------|
| 给现有系统打补丁 | 不需要改前端代码，在服务器端新增表+触发器即可扩展功能 |
| 系统间数据同步 | 通过触发器在A系统的数据变更时自动同步到B系统 |
| 复杂完整性约束 | CHECK 约束不支持 IF/WHILE 等复杂逻辑，触发器可以 |
| 业务规则集中管理 | 规则写在服务器端，前端零改动即可适配变化 |

> [29:36-33:15] 两个系统需要数据交互时，直接访问对方的数据库一般是不被允许的（责任划分问题）。可以开放视图来做隔离，或者通过触发器 + 新表的方案来做接口。

> [19:45-21:00] 以前做 CS 架构时，业务逻辑全在客户端。后来转向 BS 架构，很多公司把业务逻辑写成**存储过程**部署在服务器端，前端只负责界面交互——触发器与存储过程本质上都是部署在服务器端运行的代码。

### 触发器的限制

- 触发器的创建者必须是表的拥有者（对表有相应权限）
- 触发事件主要是 INSERT、DELETE、UPDATE，查询一般不需要
- 删除触发器：`DROP TRIGGER trigger_name;`

## 七、第五章完整性回顾

在进入新一章之前，老师回顾了第五章（数据库完整性）的核心：

| 概念 | 关键记忆词 |
|------|-----------|
| 实体完整性 | 主码 / 主键——定义表第一件事 |
| 参照完整性 | 外键 / 外码——数据之间的约束关系 |
| 用户定义完整性 | CHECK 约束、默认值——在域之上进一步约束取值范围 |
| 断言（ASSERTION） | 可在数据库级定义的全局约束（不依附于特定表） |
| 域（DOMAIN） | 在已有数据类型基础上自定义带约束的数据类型 |
| 触发器 | 补充 CHECK 无法处理的复杂完整性约束 |

> [44:45-48:02] CHECK 不支持 IF/WHILE 等复杂逻辑，所以复杂的完整性约束需要用触发器来补充实现。
