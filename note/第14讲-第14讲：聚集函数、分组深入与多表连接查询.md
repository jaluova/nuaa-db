## LIKE 通配符补充：转义字符

当要匹配的字符串本身就包含 `%` 或 `_` 时，需使用转义字符（ESCAPE）。

**示例**：查询以 `DB_` 开头的课程。`LIKE 'DB\_%' ESCAPE '\'`——反斜杠告诉 DBMS 其后的下划线是普通字符，而非通配符。

> 转义字符与字符集紧密相关。安装 Oracle 等 DBMS 时必须选择字符集编码（推荐 UTF-8），若前端浏览器编码与后端数据库存储编码不匹配，汉字将显示为乱码。

## 聚集函数（Aggregate Functions）

SQL 支持的聚集函数：

| 函数 | 功能 | 特殊选项 |
|------|------|---------|
| `COUNT(*)` | 统计记录总条数 | — |
| `COUNT([DISTINCT] 列名)` | 统计该列非空值个数 | `DISTINCT` 去重后计数 |
| `SUM([DISTINCT] 列名)` | 求和 | `DISTINCT` 去重后求和 |
| `AVG([DISTINCT] 列名)` | 求平均值 | `DISTINCT` 去重后求平均 |
| `MAX(列名)` | 求最大值 | — |
| `MIN(列名)` | 求最小值 | — |

### DISTINCT 在聚集函数中的用法

`COUNT(sno)` 与 `COUNT(DISTINCT sno)` 的区别：

- 从**学生表**查学号：学号天然不重复，两者结果相同。
- 从**选课表**查学号：一个学生可能选多门课，不加 DISTINCT 统计的是选课人次，加 DISTINCT 统计的是选课人数。若存在重名学生的姓名列，`COUNT(sname)` 和 `COUNT(DISTINCT sname)` 也将不同。

`COUNT(*)` 统计所有记录（包括全 NULL 行）；`COUNT(列名)` 仅统计该列非空的行。

### 用排序 + LIMIT 替代 MAX/MIN

求最高分除了用 `MAX(grade)`，也可用 `ORDER BY grade DESC LIMIT 1` 实现，结果等价。这体现了 SQL 的多途径实现特性。

### 无 GROUP BY 时聚集函数的作用范围

若 SELECT 语句中没有 `GROUP BY`，聚集函数作用于**整个查询结果集**（经 WHERE 过滤后的全部记录），返回单行结果。

## GROUP BY 深入与 HAVING

### 分组规则重申

使用 `GROUP BY` 后，SELECT 子句中的非聚集列**必须出现在 GROUP BY 中**，否则 DBMS 拒绝执行。不在 GROUP BY 中的列若要出现在 SELECT 中，**必须套上聚集函数**。

> 这条规则的本质原因：分组后每组有多条记录，未分组的字段在每个组内可能有多个不同值，DBMS 无法确定输出哪一个。只有分组字段（组内唯一）和聚集结果（将多值归约为单值）才能确定性地输出。

### GROUP BY 后可使用表达式

统计每个年级的学生人数时，学号的前 4 位代表年级，可以这样写：

```sql
SELECT LEFT(sno, 4) AS grade, COUNT(*) AS cnt
FROM student
GROUP BY LEFT(sno, 4);
```

`GROUP BY` 后面不仅可以跟原始字段名，也可以跟基于字段的表达式。

### HAVING 与 WHERE 的本质区别

| 维度 | WHERE | HAVING |
|------|-------|--------|
| 作用时机 | **分组前**，对原始记录逐行过滤 | **分组后**，对每组结果进行判定 |
| 能否含聚集函数 | 不能 | 能（如 `AVG(grade) > 90`） |
| 执行顺序 | 先 WHERE 过滤，再 GROUP BY 分组 | 先 GROUP BY 分组，再 HAVING 筛选组 |

**示例对比**：

```sql
-- 正确：查询每个平均成绩 >= 90 的学生的学号和平均成绩
SELECT sno, AVG(grade)
FROM sc
GROUP BY sno
HAVING AVG(grade) >= 90;

-- 错误：WHERE AVG(grade) >= 90 是对全表所有成绩求平均后判断
-- 若全表平均成绩不足 90，整个查询返回空结果
```

> WHERE 是对全表数据"一刀切"的过滤；HAVING 是对每个分组"各自判断"是否保留。两者适用的范围完全不同，这是考试中的高频考点。

## 多表连接查询

连接查询是查询操作中**最耗时**的部分。实际开发中，某些公司甚至会限制单条 SQL 语句中参与连接的表数量。

### 连接的本质：双重循环

两张表做连接的底层实现相当于**嵌套循环**：

1. 外层循环遍历外表（驱动表）的每一条记录。
2. 内层循环遍历内表的每一条记录，判断是否满足连接条件。
3. 如果连接条件没有排序和索引支撑，内表可能被遍历 n 次（n = 外表记录数），产生大量磁盘 I/O。

> **优化直觉**：既然外表只需遍历一次、内表要遍历多次，那么**外表应该放小表，内表放大表**，以减少内表反复读盘的次数。

### DBMS 的三种连接实现策略

| 策略 | 条件 | 原理 | I/O 代价 |
|------|------|------|---------|
| 嵌套循环连接（Nested Loop Join） | 无排序、无索引 | 双重循环，内表每次从头扫描 | 最大（内表读 n 遍） |
| 排序归并连接（Sort-Merge Join） | 连接字段已排序 | 两表各遍历一次；遇到不匹配时可提前终止内循环 | 较小 |
| 索引连接（Index Join） | 连接字段建有索引 | 通过索引直接定位匹配记录，无需扫描 | 最小 |

> 排序归并连接的关键优化：当连接字段有序时，外表某条记录在内表中找到第一条不匹配的记录后，即可提前终止内循环（因为后续的记录也不可能匹配）。此时内表和外表都只需遍历一次。

实际执行时 DBMS 会根据表的**当前状态**（是否有索引、是否已排序、数据量大小）自动选择最优连接策略。

### 多表连接条件数量

n 张表连接，至少需要 n-1 个连接条件。如果漏写连接条件，DBMS 将产生**笛卡尔积**——两张百万行的表做笛卡尔积会得到万亿行，可能长时间无法返回结果。

### 等值连接与自然连接

`FROM student, sc WHERE student.sno = sc.sno` 是典型的等值连接。若去除 WHERE 条件，得到的就是笛卡尔积。

> 在 SQL 中，连接条件与查询条件都写在 WHERE 中，DBMS 先从笛卡尔积中过滤出满足连接条件的行（等值连接），再从中过滤出满足查询条件的行。

## 自身连接（Self Join）

当查询涉及同一张表的两个不同角色时，需将表与自身连接。做法：给同一张表取**两个不同的别名**，当作两张独立的表使用。

**示例**：查询每门课程的间接先行课程（先行课程的先行课程）。

```sql
SELECT first.cno, second.cpno
FROM course first, course second
WHERE first.cpno = second.cno;
```

- `first` 别名视为"第一张课程表"（取其先行课程编号）
- `second` 别名视为"第二张课程表"（取其课程编号）
- 连接条件：第一张表的先行课程编号 = 第二张表的课程编号
- 输出：第一张表的课程编号 和 第二张表的先行课程编号（即间接先行课）

> 自身连接的关键在于**取别名区分**。逻辑上就是两张结构和数据完全相同的表做连接。

## 外连接（OUTER JOIN）

等值连接（内连接）会**丢弃**无法匹配的记录。若需保留某侧的全部记录，匹配不上的以 NULL 填充，则需使用外连接：

| 类型 | 语法 | 含义 |
|------|------|------|
| 左外连接 | `FROM A LEFT OUTER JOIN B ON ...` | 保留左表全部记录 |
| 右外连接 | `FROM A RIGHT OUTER JOIN B ON ...` | 保留右表全部记录 |

**典型场景**：输出所有学生的基本信息及其选课情况。若某个学生未选任何课，等值连接会导致该学生在结果集中消失；而左外连接（学生表在左）会保留该学生，其选课信息列以 NULL 填充。

```sql
SELECT student.*, sc.*
FROM student LEFT OUTER JOIN sc ON student.sno = sc.sno;
```

## 嵌套查询入门（子查询）

将一条 SELECT 语句嵌入另一条 SELECT 语句的 WHERE 或 HAVING 中，形成**子查询**。

**示例**：查询选修了 2 号课程的学生的姓名。

```sql
SELECT sname
FROM student
WHERE sno IN (
    SELECT sno FROM sc WHERE cno = '2'
);
```

执行顺序：先执行内层子查询，得到一个学号集合；再将该集合代入外层查询的 IN 条件中。此时子查询结果是**静态的**，相当于一个常量集合。

> 嵌套查询中，子查询的 SELECT 后面通常只出现一个列（用于与外层比较），且子查询中不能使用 ORDER BY——排序对作为集合使用的子查询结果没有意义。
