## 组织架构的数据库设计

### 树状结构的表示

> [02:14] 组织架构是典型的树状结构（学校 -> 学院 -> 系/教研室）。用关系型数据库的二维表如何表示？

**基本设计**：

| 字段 | 说明 |
|------|------|
| `ID` | 部门编号（主码） |
| `Name` | 部门名称 |
| `ParentID` | 上级部门编号（外码，参照本表ID） |

```
南航(ID=01, ParentID=NULL ← 根节点)
├── 计算机学院(ID=10, ParentID=01)
├── 外语学院(ID=18, ParentID=01)
│   ├── 英语一系(ID=1801, ParentID=18)
│   └── 英语二系(ID=1802, ParentID=18)
```

> [04:36] `ParentID` 不是本关系的主码，但它参照本关系的 `ID`，因此构成**自身参照完整性**。`ParentID` 可以取 `ID` 中存在的值，也可以为空（根节点为空）。

### 设计考虑：后续统计的易用性

- 如果编码**有规则**（如层级编码），统计时可用前缀匹配
- 如果编码**无规则**，需要用 `IN` 子句或递归方式统计

> [15:32] 做表设计时就要考虑后续功能的实现。不同的设计方案，后续实现的难易程度差别很大。

**统计某院系（含下属）人数的方法**：
1. 找到该节点的所有子孙部门编号（树遍历）
2. 用 `WHERE Dpid IN (部门编号集合)` 统计职工人数
3. 或通过递归方式累加

## 复杂SQL查询示例

### 示例1：查询比经理工资高的雇员（自连接）

**问题**：查询工资比其经理高的雇员姓名和工资。

**分析**：职工表中每人有 `Empno` 和 `Mgr`（经理编号），经理也是职工表中的一条记录。

**方法一：嵌套子查询**

```sql
SELECT Ename, Salary
FROM Emp E1
WHERE Salary > (
    SELECT Salary FROM Emp E2
    WHERE E2.Empno = E1.Mgr
);
```

**方法二：自连接**

```sql
SELECT E1.Ename, E1.Salary
FROM Emp E1, Emp E2
WHERE E1.Mgr = E2.Empno
  AND E1.Salary > E2.Salary;
```

> [19:25] 同一张表在查询中可以用多次，但必须给每个实例取**不同的别名**，系统才能区分。

### 示例2：查询雇员人数相同的部门（GROUP BY + HAVING）

**要求**：输出人数相等的部门的部门号和雇员人数。

```sql
SELECT Dpid, COUNT(*)
FROM Emp
GROUP BY Dpid
HAVING COUNT(*) IN (
    SELECT COUNT(*)
    FROM Emp
    WHERE Dpid <> 当前部门的Dpid  -- 排除自身
    GROUP BY Dpid
);
```

> [23:24] 核心逻辑：外层按部门分组统计人数，HAVING条件判断当前部门人数是否在"其他各部门的人数集合"中出现。为什么要用 `IN` 而不用 `=`？因为有多个部门可能人数相同，后面返回的是一个集合，不能用等号。

**判断准则**：
- 子查询返回**单个值** -> 可用 `=`
- 子查询返回**多个值（集合）** -> 必须用 `IN`

### 示例3：创建含日期函数的视图

```sql
CREATE VIEW CS_Emp
AS
SELECT Ename, Hiredate
FROM Emp
WHERE Dpid = 'CS'
  AND Hiredate > '2020-01-01';
```

> [28:50] 不同DBMS系统的日期转换函数表达方式不同。考试时可按书上写，也可按你实际使用的DBMS写法写。

## 第四章：数据库安全性

### 为什么关注安全？

> [32:16] 本专业是信息安全专业。数据库系统在数据共享与安全隔离之间需要做**平衡**——共享是为了使用，安全需要隔离。

### 数据库面临的安全威胁

| 威胁类型 | 说明 |
|---------|------|
| 非授权用户访问数据库 | 绕过DBMS直接读写数据文件（早期DBASE/FoxBASE一个表一个文件，结构透明） |
| 应用程序执行非授权操作 | 用户获得不应有的功能权限 |
| 通过合法操作推导隐藏信息 | 多次合法查询后通过分析获得敏感数据 |

现代DBMS（如SQL Server、MySQL）将数据文件和字典打包成大文件，结构不公开，直接读写变困难。

### 数据库系统安全层次

从外到内：
1. **用户标识与鉴别**——用户名/密码
2. **访问控制（授权）**——哪些用户能做什么操作
3. **视图机制**——隔离不同用户看到的数据范围
4. **审计**——所有操作有迹可查
5. **数据存储加密**——密码学保护

> [34:42] 加密一定带来性能消耗（使用时要解密），实际系统中一般只对部分敏感数据加密。

### 安全标准

#### TCSEC（可信计算机系统评估准则）

| 级别 | 名称 | 说明 |
|------|------|------|
| D | 最小保护 | 安全级别最低 |
| C1 | 自主安全保护 | 基本的用户/数据分离 |
| C2 | 受控存取保护 | 审计功能，DAC可达此级别 |
| B1 | 标记安全保护 | 强制访问控制，MAC可达此级别 |
| B2 | 结构化保护 | 形式化安全模型 |
| B3 | 安全域 |  |
| A1 | 验证设计 | 最高级别，形式化验证 |

> [47:05] 当前大多数商业操作系统和数据库系统仅能达到 **C1-C2 级别**。B2级以上主要应用于军事、航空等特殊领域。理论上，做到形式化测试与验证的系统才能称为"可信系统"。

#### CC标准（通用准则）

将安全分为两方面：
- 安全功能要求（有哪些安全保障措施）
- 安全保障要求（如何落实这些措施）

CC分7级，与TCSEC各级可一一对应。

> [46:46] 所有安全标准本质上就是两大块：一是**制定安全策略和制度**，二是**靠谁去执行和落实**。
