## 海量转储与增量转储

转储的分类除了静态/动态维度外，还有另一个划分维度。

**海量转储**（全量备份）：每次备份整个数据库的全部数据 [00:49]。相当于完整覆盖式的拷贝。

**增量转储**：只转储自上次备份以来发生变化的数据部分 [01:13]。上一次备份到当前备份时刻之间，可能只有部分数据发生了改变，仅备份这些变化即可。

将两个维度交叉组合，共有**四种转储策略**：静态海量、静态增量、动态海量、动态增量。

### 静态转储的一致性保证

> [02:40] 在做数据转储之前，DBMS 一定会强制写缓冲——把缓冲里面的数据强制性地写回到磁盘上面去，保证转储之前所有已完成事务的数据真实地反映到磁盘文件上面。

这意味着：转储时间点之前的所有已完成事务，恢复时无需再做 REDO——其数据已确定性地反映在备份副本中 [03:17]。

## 动态转储下的不一致问题

动态转储允许事务与备份并发执行，但这带来了副本数据不确定的问题。

教师以时间轴为例说明 [07:55]：设转储从时间 $$T_B$$ 开始到 $$T_E$$ 结束。在转储期间的某一时刻 $$t$$，系统将数据 A = 100 写入磁盘并备份；随后在另一时刻 $$t'$$，另一个事务将 A 修改为 200。备份结束时，副本文件中的 A 是 100——但这个值并不正确。

> [09:16] 备份以后在后面的执行过程当中，又有一个地方把它改成 200 了。备份结束以后，备份文件当中的 A 是 100，但是这个 A 是正确的吗？不正确。

结论：动态转储不能保证副本数据的正确性，后续恢复时必须结合日志文件补全 [10:09]。

## 动态转储下的事务恢复策略——考试重点图示

教师用时间轴图分析了动态转储下的关键场景 [10:09]。设转储时间段为 $$T_B \\to T_E$$，故障发生在 $$T_F$$：

### 事务 T4（$$T_B$$ 前已完成）

无需任何操作。因为转储前强制写缓冲已保证其数据正确反映在副本中 [13:12]。

> [13:27] 在这个点之前的所有已完成的事务，我们都可以不管。因为备份文件已经反映了状态。

### 事务 T5、T6（跨备份区间，故障前已完成）

属于已完成事务，但数据因跨备份期间而不一定完全反映在副本中 [14:37]。恢复策略：**REDO**。

> [18:52] 相对故障点来讲，它属于已完成的事物。但是我们反过来讲，相对备份的起点来讲，它的数据并不一定百分之百反映在备份文件当中。所以说对这种事物是 REDO。

### 事务 T7、T8（备份区间开始或之后，故障时未完成）

故障发生时事务尚未完成，但其修改可能已部分反映。恢复策略：**UNDO**。

教师反复强调 [18:10]：判断恢复策略的核心依据始终是两条——故障发生时该事务是否已完成、该事务的数据是否确定反映在备份副本中。

## 船岸数据同步——增量转储的实际应用

教师分享了一个来自海事局船舶管理系统的实际项目经验 [20:28]。

船在海上独立运行，无法与岸基中心机房实时联网。解决方案：
- 船上系统在 DBMS 之外自建日志，记录所有数据更新操作（本质上就是 INSERT、DELETE、UPDATE 语句）
- 靠岸时将记录的 SQL 语句（而非数据本身）同步到岸基重新执行

> [22:43] 我执行的是相当于把 SQL 语句传过来了，不是传的数据本身。从某种意义上也是属于一种增量的数据同步。

这本质上是增量转储思想的工程应用。

## 日志文件的结构与格式

### 什么是日志文件

日志文件（Log File）是按时间顺序记录事务对数据库所有**更新操作**（INSERT、DELETE、UPDATE）的流水文件 [25:09]。查询操作（SELECT）对数据库状态无影响，不记录在日志中。

> [25:21] 大量的查询操作对数据库的状态有没有影响？没影响。更新操作记录在日志文件当中。

### 两种日志格式

**以记录为单位的日志文件** [26:59]：记录每一条 SQL 更新语句（操作级日志）。

**以数据块为单位的日志文件** [27:11]：记录数据块在更新前后的状态变化（物理级日志），粒度更粗但数据量更小。

### 以记录为单位的日志——具体结构

每条日志记录包含以下字段 [30:25]：

| 字段 | 说明 |
|------|------|
| 事务标识 | 该操作属于哪个事务 |
| 操作类型 | INSERT / DELETE / UPDATE（可简化为 I / D / U） |
| 操作对象 | 对哪些数据对象进行操作 |
| 更新前数据旧值 | Before Image——UNDO 的依据 |
| 更新后数据新值 | After Image——REDO 的依据 |

旧值与新值在不同操作类型下的存在性（考试易考点）[31:26]：

| 操作类型 | 旧值 | 新值 |
|---------|------|------|
| INSERT | 无（插入前不存在） | 有（插入的新记录值） |
| DELETE | 有（被删除的记录内容） | 无（删除后不存在） |
| UPDATE | 有（更新前的值） | 有（更新后的值） |

> [32:40] 你 DELETE 把这个数据干掉了，数据不存在了。所以说更新前的旧值对于不同的操作代表的内容是不同的。插入是没有的，更新的时候肯定是更新前的值，删除的时候就是删除前的值。

旧值用于 UNDO（恢复到更新前的状态），新值用于 REDO（重新应用到数据库）。

## 从日志文件识别事务状态

判断事务是否完成的关键逻辑 [27:33]：

- 在日志文件中能找到某事务的 **BEGIN 标记**和**COMMIT（或 ROLLBACK）标记** $$\\to$$ 该事务**已完成**
- 只有 BEGIN 标记，找不到 COMMIT 或 ROLLBACK $$\\to$$ 该事务**未完成**

> [28:27] 在日志中能查到这个事务的 BEGIN 操作，但是在后续找不到这个事务的 COMMIT 和 ROLLBACK，说明这个事务在执行的时候一切操作记录下来了，中间出问题了。

### 写日志与写数据库的顺序

> [38:49] 你们觉得 DBMS 应该是先写日志文件，还是先写数据文件？是不是有个先后顺序的问题？

答案：**必须先写日志文件，后写数据文件** [39:59]。

原因分析 [39:19]：如果先写数据再写日志，中间崩溃则数据已变但无记录可查，成为一个"没有源头的变动"，无法恢复。反之，先写日志，即便写入数据时崩溃，也可以按日志 REDO 恢复。

> [39:59] 先把流水账记好，记好了以后再去真正改数据。如果中间出了问题，可以按照流水去重做或者做撤销，确保数据状态正确。

教师建议：日志文件与数据文件应部署在**不同物理磁盘**上以提高可靠性 [41:48]。只要日志文件正确存在，就有办法保证数据文件的正确性。

## 事务故障恢复的 UNDO 算法

事务故障属于未完成事务，恢复策略为 UNDO [43:45]。

恢复步骤 [44:36]：

1. **反向扫描**日志文件（从最后一条记录向前扫描）
2. 查找该事务的所有更新操作记录
3. 对每条更新操作执行**逆操作**

逆操作对应关系 [45:17]：
- INSERT $$\\to$$ DELETE（将多插的记录删除）
- DELETE $$\\to$$ INSERT（将删掉的记录重新插入）
- UPDATE $$\\to$$ 用旧值重新 UPDATE

> [44:58] 在日志当中原来已经记录了更新操作之前的数据状态和更新之后的数据状态，利用这里面的记录，就可以做反向操作。

重复上述步骤，直到该事务的 BEGIN 标记为止。教师指出这种每次都扫描到日志开头的方式效率太低，引出后续的**检查点机制** [45:59]。

## 系统故障恢复算法——两个队列

系统故障可能同时造成两类事务需要处理，因此恢复算法需要先行分类。

恢复步骤 [47:08]：

1. **正向扫描**日志文件（从开头向后）
2. 建立两个队列：
   - **UNDO 队列**：所有未完成的事务（有 BEGIN 但无 COMMIT/ROLLBACK）
   - **REDO 队列**：所有已完成的事务（有 BEGIN 且有 COMMIT）
3. 先对 UNDO 队列中事务执行 UNDO（反向扫描做逆操作）
4. 再对 REDO 队列中事务执行 REDO（正向扫描重新执行）

> [04:17] 对 UNDO 队列当中的事务进行 UNDO 操作。做 UNDO 操作是反向扫描日志文件，按照事务执行过程的倒序，将每个事务进行更新操作的逆操作。

教师提到教材第 331 页第 4 题是一道典型的考试题型 [05:23]：给出事务执行时间序列表（含 T1 至 T4 的读写操作顺序及 COMMIT 时间点），要求判断各事务归属哪个队列并写出恢复操作。这是**考试基本要求**，每个事务 1 分。
