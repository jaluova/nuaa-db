# 第3章 SQL 数据操纵 & 第4章 数据库安全性

## SQL 数据更新

### 插入数据 (INSERT)

```sql
INSERT INTO 表名 [(属性列...)] VALUES (值...)
```

- 值的个数和位置必须与属性列一一对应
- 不写属性列时，必须按表定义顺序给出所有列的值
- 如果某列值未知，可以给 **NULL**（前提是该列允许空值）
- 也可以嵌入子查询实现批量插入

### 修改数据 (UPDATE)

```sql
UPDATE 表名 SET 列名 = 表达式 [, ...] [WHERE 条件]
```

**要点：**
- SET 左边必须是**列名**（字段变量），不能是表达式
- 表达式可以包含字段变量、算术运算符等
- 修改可能涉及子查询（如：将计算机系所有学生的成绩归零需要关联学生表判断所在系）

**执行过程理解：**
外循环遍历要更新的表（如 SC），逐条取出记录 → 根据条件判断（可能子查询） → 满足则更新，不满足则跳过

### 修改操作与完整性约束

修改时必须遵循三类完整性约束：

1. **实体完整性**：主码不能重复、不能为空。修改主码必须保持唯一且非空。
2. **参照完整性**：
   - 修改被参照表的主码 → 参照表中的外码需要同步处理
   - 两种策略：**不允许修改** 或 **级联更新**（CASCADE，DBMS 自动同步）
   - 修改参照表的外码 → 新值必须在被参照表的主码中存在（或为空）
3. **用户定义完整性**：如默认值、CHECK 约束等

### 删除数据 (DELETE)

```sql
DELETE FROM 表名 [WHERE 条件]
```

- 删除整条记录，不能只删部分列
- 无条件 WHERE 则删除全部记录（表变空）
- **删除只能针对单表**，不能写连接（与查询不同）

**示例：** 删除计算机系所有学生的选课记录
```sql
DELETE FROM SC
WHERE SNO IN (SELECT SNO FROM Student WHERE Sdept = 'CS')
```
或关联写法：
```sql
DELETE FROM SC
WHERE EXISTS (SELECT * FROM Student WHERE Student.SNO = SC.SNO AND Sdept = 'CS')
```

两种写法功能相同但**执行效率不同**，实际系统尽量避免用 IN。

### 删除操作与完整性约束

- 删除被参照表记录时，参照表中的关联记录存在两种策略：
  - **不允许删除**（有选课记录的学生不能删）
  - **级联删除**（CASCADE DELETE）——慎用！误删可能连锁清掉大量数据

## 空值 (NULL)

### 概念

- 空值是数据库中的特殊常量，表示"未知"、"不存在"或"无意义"
- **不是空字符串，不是 0**，而是一个特殊的标记
- 高级语言中通常没有对应的概念（变量即使不赋值也有随机值）

### 使用场景

- 选课表中的成绩列：学生选课后暂无成绩，不能设默认值 0（因为 0 分是合法成绩），用 NULL 最合适
- 取消成绩：将成绩设为 NULL 即可，不删记录

### 判断空值

```sql
IS NULL      -- 不能用 = NULL
IS NOT NULL  -- 不能用 != NULL
```

### 约束规则

- **主码不能为空**（实体完整性）
- **外码逻辑上可空**（参照完整性允许），但若同时是主码属性则不可空
  - 如选课表的学号：既是外码（参照学生表），又是联合主码的一部分，受实体完整性约束 → **不能为空**

### 运算规则

- 空值与任何值算术运算 → 结果为空
- 空值与另一个值比较 → 结果为 **unknown**（不确定）
- 三值逻辑：`TRUE` / `FALSE` / `UNKNOWN`

逻辑运算表：

| X | Y | X AND Y | X OR Y | NOT X |
|---|---|---------|--------|-------|
| T | U | U | T | F |
| F | U | F | U | T |
| U | T | U | T | U |
| U | F | F | U | U |

- WHERE 条件中只有结果为 TRUE 的记录才会被返回，FALSE 和 UNKNOWN 都不会

**实际意义：** 查询不及格学生时，需额外处理成绩为空（缺考）的记录：
```sql
WHERE Grade < 60 OR Grade IS NULL
```

## 视图 (View)

### 基本概念

- 视图是**虚表**（逻辑表），只存放定义，不存放实际数据
- 数据来源于基本表或已有视图，在访问时动态从基本表中抽取
- 可基于表或视图定义视图，支持多层次

### 创建视图

```sql
CREATE VIEW 视图名 [(列名...)]
AS 子查询
[WITH CHECK OPTION]
```

- 子查询中**不能**含有 `ORDER BY` 和 `DISTINCT`
- 创建时不执行子查询，仅在数据字典中保存定义
- 省略列名时，默认使用子查询中的列名
- 可自定义列名，实现**列名隔离**（对用户隐藏真实字段名）

**`WITH CHECK OPTION`：**
- 在对视图做插入/更新时，DBMS 自动加上创建视图时的 WHERE 条件
- 保证视图中的数据始终满足视图定义条件
- 如：信息系视图 + WITH CHECK OPTION → 插入的学生自动设为信息系，修改时只改信息系学生

### 查询视图

- 对视图查询 = 对基本表查询，DBMS 自动完成转换
- **转换过程：** 将视图查询的 WHERE 条件 + 视图定义中的 WHERE 条件合并，转化成对基本表的查询

**示例：**
```sql
-- 视图定义
CREATE VIEW IS_Student AS
SELECT Sno, Sname, Sage FROM Student WHERE Sdept = 'IS'

-- 用户查询
SELECT * FROM IS_Student WHERE Sage < 20

-- DBMS 转化后实际执行：
SELECT Sno, Sname, Sage FROM Student WHERE Sdept = 'IS' AND Sage < 20
```

**关键陷阱——HAVING vs WHERE：**
```sql
-- 错误！WHERE 中不能用聚集函数
SELECT Sno, AVG(Grade) FROM SC WHERE AVG(Grade) > 90  -- 错！

-- 正确写法
SELECT Sno, AVG(Grade) FROM SC GROUP BY Sno HAVING AVG(Grade) > 90
```

### 更新视图（受限）

- 视图的增删改最终转化为**对基本表的更新**
- **更新受限**：包含聚集函数、GROUP BY、DISTINCT 的视图通常不可更新
- 如平均成绩视图中的平均成绩字段无法直接修改——改不了，因为无法映射到具体哪条基本表记录

### 视图的作用

1. **简化用户操作**：将复杂多表查询封装成"单表"，前端写简单的 SELECT 即可
2. **多角度看待同一数据**：同一张基本表可定义不同视图给不同角色使用
3. **逻辑独立性**：统计规则变化只需改视图定义，前端代码不动
4. **安全保护**（隔离）：每个学院只能看到本院学生的视图，无法访问其他学院数据
5. **更清晰的表达查询**：将业务统计逻辑沉淀在视图中

## 第4章 数据库安全性

### 安全概述

**安全本质：** 在**共享**与**隔离**之间做平衡

**数据库系统的安全层次：**
- 用户标识与鉴定（最外层）
- 存取控制（DAC / MAC）
- 视图机制（隔离）
- 审计（Audit）
- 数据存储加密（操作系统层面 / DBMS 加密功能）

**两大安全标准：**
- **TCSEC**（1985，美国）：分 D / C1 / C2 / B1 / B2 / B3 / A1 级
- **CC**（国际标准）：分 7 级，与 TCSEC 对应
- 商用系统通常只能达到 C2 级，B2 级以上需形式化验证（军事等特殊领域）
- DAC 可达 C2 级，MAC 可达 B1 级

### 用户标识与鉴别

- 最基本的安全措施：用户名 + 密码
- DBMS 安装时创建超级用户（SQL Server: `sa`，MySQL: `root`）
- 应用系统用户 ≠ 数据库用户（需单独创建 DB 用户用于连接）

### 存取控制

**两个层次：**
1. 功能的授权：哪些用户可以操作哪些功能
2. 内容的授权：同一功能下，不同用户能看到哪些数据

**数据对象粒度（从粗到细）：**
数据库 → 表 → 记录 → 分量（字段值）

- 粒度越细，控制越精确，但管理代价越大（授权登记表变大，检查变慢）
- 售票系统等并发场景：表级授权粒度过粗，会导致并发性能下降

### 自主存取控制 DAC (Discretionary Access Control)

**两条核心命令：**

#### GRANT（授权）
```sql
GRANT 权限 [, ...] ON 对象 TO 用户 [, ...] [WITH GRANT OPTION]
```
- `WITH GRANT OPTION`：允许被授权者将权限再授予他人
- 权限不能循环授予
- 只有 DBA 或对象的创建者才能授权

**示例：**
```sql
-- 把学生表的查询权限给 U1
GRANT SELECT ON TABLE Student TO U1;

-- 把学生表学号的更新权限给 U1（分量级）
GRANT UPDATE(Sno) ON TABLE Student TO U1;

-- 允许 U4 将权限再传递
GRANT INSERT ON TABLE SC TO U4 WITH GRANT OPTION;

-- 对所有用户授权
GRANT SELECT ON TABLE SC TO PUBLIC;
```

#### REVOKE（回收）
```sql
REVOKE 权限 [, ...] ON 对象 FROM 用户 [, ...] [CASCADE|RESTRICT]
```
- `CASCADE`：级联回收（收回该用户及经他传递出去的所有权限）
- `RESTRICT`：若有级联影响则拒绝回收

### 数据库角色 (Role)

- 角色是**权限的集合**，简化授权管理
- 创建角色 → 对角色授权 → 将角色授予用户

```sql
CREATE ROLE R1;
GRANT SELECT, UPDATE, INSERT ON TABLE Student TO R1;
GRANT R1 TO U1, U2, U3;
REVOKE R1 FROM U1;
```

### 强制存取控制 MAC (Mandatory Access Control)

- DAC 只控制对数据对象的操作权限，**不控制数据本身的内容级别**
- MAC 给主体和客体分别打上**敏感度标记**：
  - **主体**的敏感度 → **许可证级别**（License Level）
  - **客体**的敏感度 → **密级**（Classification）
- 级别：公开 → 可信 → 机密 → 绝密
- 按规则比配：只有许可证级别 ≥ 密级时，主体才能读客体
- 适用场景：军队、政府等涉密单位的公文管理系统
